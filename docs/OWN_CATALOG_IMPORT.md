# OWN_CATALOG_IMPORT.md — Імпорт власного каталогу книг (Milestone 11, доповнення)

## Навіщо

Власник продукту сам курує невелику (наразі ~2094 рядки) добірку книг —
`data/curated-books.csv` (`data/README.md`) — які одразу з'являються і в звичайному пошуку
застосунку (`CuratedCatalogProvider`), і як перший, найточніший кандидат для «Що почитати
завтра?». Дотепер цей файл лише документувався (`data/README.md` посилався на
`scripts/sync-curated-books.js`, якого фактично не існувало в репозиторії) — цей документ і
сам скрипт закривають цей розрив: реальний, тестований, ідемпотентний CLI-пайплайн, що масштабується
на наступні 10 000 книг без жодної зміни коду застосунку, не лише на сьогоднішній файл.

Це **не новий застосунок і не нова архітектура** — лише реалізація того, що документація вже
обіцяла, побудована на наявних сутностях (`curated_book`, `book-covers` Storage bucket,
`GenreRepository.SEED_GENRES`, `RecommendationPurpose`) без жодної нової таблиці, RPC чи
залежності.

## Архітектурний контекст — куди саме імпортуються дані

У проєкті ТРИ окремі поняття "каталогу", і плутати їх небезпечно:

1. **`curated_book`** (Supabase, `supabase/schema.sql`) — та таблиця, куди пише ЦЕЙ пайплайн.
   Власник курує вручну/пакетно, `service_role`-only запис, `SECURITY DEFINER` RPC-читання
   для anon/authenticated. Навмисно **плоска**: `authors`/`genres`/`purposes` — прості
   `text[]`, БЕЗ Work/Edition/Author/Genre join-таблиць. Дедублікація й апдейти йдуть за явним
   `id` (слаг), не за розпізнаванням "яка це книга" з невизначеності.
2. **`catalog_book`** (Supabase) — окрема, краудсорсна таблиця: наповнюється клієнтськими RPC,
   коли користувачі підтверджують додавання книги (`docs/SHARED_CATALOG.md`). Цей пайплайн
   **НІКОЛИ** її не торкається.
3. **Локальний Work/Edition/Author** (SQLite, кожен пристрій) — особиста бібліотека
   користувача. Цей пайплайн їх не створює й не чіпає взагалі: коли користувач додає результат
   пошуку (в т.ч. з `curated_book`) у свою бібліотеку, локальні Work/Edition створюються
   автоматично, без жодних змін, тим самим наявним `BookMetadataProvider`/
   `NormalizedBookDraft`-потоком, що вже обробляє Google Books/ISBNdb.

Тому "Work vs Edition" розрізнення з ТЗ тут не застосовується буквально — `curated_book` не має
власного Work/Edition поділу; кожен рядок CSV = один запис `curated_book` = один майбутній
Edition-кандидат, коли (і якщо) користувач додасть його собі.

## Формат CSV

Той самий header, що вже реально використовує `data/curated-books.csv` й документує
`data/README.md` (не вигадано наново — ТЗ явно велить адаптувати до наявного формату, якщо він
є):

```
id,title,authors,isbn13,isbn10,page_count,cover_url,description,genres,purposes,language,is_active
```

Повний опис кожної колонки, дозволені жанри — `data/README.md`. `data/catalog-import-template.csv`
— готовий валідний приклад (2 рядки) для копіювання під новий файл; сам пройшов dry run без
жодної помилки чи попередження.

`authors`/`genres`/`purposes` — списки через `;` в ОДНІЙ CSV-клітинці (RFC4180-парситься як
завжди, `;` розбирається вже після — це відповідальність вищого рівня, не самого CSV-парсера).

## Пайплайн

```
RAW CSV → PARSE → VALIDATE → NORMALIZE → DEDUPLICATE → DOWNLOAD COVER → VALIDATE IMAGE →
UPLOAD TO OWN STORAGE → UPSERT CATALOG → CREATE IMPORT REPORT
```

Реалізація — окремі, чисті, незалежно тестовані модулі в `scripts/catalog-import/`, зібрані
докупи `scripts/sync-curated-books.js`:

| Крок | Модуль | Що робить |
| --- | --- | --- |
| PARSE | `csv.js` | Справжній RFC4180-парсер (лапки, екранування подвоєнням, багаторядкові поля, BOM) — НІКОЛИ не `split(',')`. |
| VALIDATE | `validate.js` | Перевіряє КОЖЕН рядок незалежно — один невалідний рядок не валить увесь файл. Помилки (`error`) блокують рядок, попередження (`warning`) — ні. |
| NORMALIZE | `normalize.js` | Тільки для рядків, що пройшли валідацію: розбиває списки, обчислює ISBN-еквіваленти, тримає, типізує `page_count`/`is_active`. |
| DEDUPLICATE | `dedupe.js` | В межах ОДНОГО файлу: той самий `id` двічі (попередження, останній перемагає) і РІЗНІ `id` з ОДНАКОВИМ ISBN (помилка, другий виключається — інакше апсерт впав би на unique-обмеженні). |
| DOWNLOAD/VALIDATE/UPLOAD COVER | `cover.js` | Див. розділ нижче. |
| UPSERT CATALOG | `supabaseAdmin.js` | `POST /rest/v1/curated_book?on_conflict=id`, `Prefer: resolution=merge-duplicates` — той самий ефект, що `ON CONFLICT (id) DO UPDATE`. |
| CREATE IMPORT REPORT | `report.js` | Збирає totals + row-level issues у JSON і текст. |

Оркестрація, CLI-прапорці, `.env`-читання — `scripts/sync-curated-books.js`.

### Чому CommonJS, а не TypeScript

`scripts/**/*.js` уже виключено з `eslint.config.js` з коментарем, що анципує "прості CommonJS
Node-скрипти поза застосунком" — сам проєкт заздалегідь підготував саме таку архітектуру. У
проєкті немає `ts-node`/`tsx`, тож прямий імпорт `src/lib/*.ts` з Node CLI-скрипта неможливий
без нового інструменту збірки. Замість цього — той самий підхід, що вже задокументований у
`supabase/functions/isbndb-proxy/isbn.ts` (навмисна часткова дублікація `src/lib/isbn.ts` для
Deno, бо той рантайм так само не може імпортувати React Native `src/`): `csv.js`/`isbn.js` у
цій теці — свідомі, задокументовані часткові дублікати `src/lib/csv.ts`/`src/lib/isbn.ts`,
підтверджені тестами (`isbn.test.js`/`csv.test.js`), що поводяться ідентично оригіналу на тих
самих прикладах. **Жодної нової npm-залежності** для всієї фічі — `src/lib/csv.ts` сам
документує проєктну політику уникати нових залежностей, де це реально; Node ≥22
(`package.json` `engines`) уже має вбудовані `fetch`/`crypto.randomUUID`/стрімінг, нічого
додаткового не знадобилось.

## Дедублікація й ISBN

Пріоритет: ISBN-13 → ISBN-10 → явний `id`. `isbnEquivalents` (`isbn.js`, та сама логіка, що
`src/data/remote/catalogSync.ts`'s `resolveIsbnPair`) заповнює ОБИДВА поля еквівалентом, коли
CSV дав лише одне — інакше два рядки, що описують ту саму книгу різними формами ISBN, не
впіймались би конфліктом.

"Title+contributor fallback" (четвертий рівень пріоритету дедуплікації з ілюстрації ТЗ) тут
**навмисно не реалізований**: `curated_book` апсертиться за явним `id`, тож резолвити "яка це
книга" за назвою просто нема коли — ключ завжди явний. Код `AMBIGUOUS_WORK_MATCH` лишається
задокументованим у `errorCodes.js` про запас, наразі недосяжний.

Реальна перевірка на `data/curated-books.csv` (2094 рядки) знайшла РІВНО один такий конфлікт:
`kuznietsova-drabyna`/`kuznietsova-e-book-drabyna`, обидва заявляють ISBN13 `9789664480977` —
другий рядок виключається з імпорту (`DUPLICATE_ISBN`), перший імпортується нормально.

## Cover-пайплайн — обкладинка НІКОЛИ не лишається посиланням на ретейлера

1. **Download** (`downloadCoverBytes`) — стрімом, з жорсткою межею 5 МБ (той самий ліміт, що
   `book-covers` bucket), таймаут 15с, до 3 спроб з backoff **лише** на 429/5xx (НІКОЛИ на 404
   чи інший постійний 4xx — ретраїти зламане посилання марно).
2. **Validate** (`sniffImageType`) — за РЕАЛЬНОЮ сигнатурою байтів (JPEG `FF D8 FF`, PNG
   8-байтова сигнатура), не за `Content-Type` заголовком чи розширенням у URL — HTML-сторінка
   помилки під виглядом `.jpg` відхиляється тут (`COVER_INVALID_IMAGE`), той самий алгоритм, що
   `supabase/functions/cover-upload/index.ts`.
3. **Upload у ВЛАСНЕ сховище** (`uploadCoverBytes`) — напряму в Supabase Storage bucket
   `book-covers` через `service_role` (`{SUPABASE_URL}/storage/v1/object/book-covers/
   {uuid}.{ext}`), та сама адреса/заголовки/шлях-конвенція, що вже використовує
   `cover-upload` Edge Function для фото користувачів — але НЕ через саму цю функцію: вона
   rate-limited (100 запитів/добу — розрахована на одне фото одного користувача, не на пакетне
   завантаження тисяч обкладинок).

**Джерело (`cover_url` з CSV) ніколи не потрапляє в `curated_book.cover_url`** — та колонка
завжди або порожня, або власний `https://{project}.supabase.co/storage/v1/object/public/
book-covers/{uuid}.{ext}` URL. Джерело зберігається лише як `coverSourceUrl` у пам'яті під час
імпорту — жодна колонка Supabase (нема `cover_source_url`/`book_source`) його не тримає,
провенанс потрапляє тільки в `{batchId}-normalized.json`, файл на диску власника, не в UI.

Відмова обкладинки (мережа/невалідне зображення/завеликий файл) **не валить імпорт книги** —
книга все одно апсертиться, `cover_url` лишається попереднім значенням (якщо було) або `null`,
причина відмови йде в звіт (`COVER_DOWNLOAD_FAILED`/`COVER_HTTP_ERROR`/`COVER_INVALID_IMAGE`/
`COVER_TOO_LARGE`/`COVER_UPLOAD_FAILED`, усі — `warning`, не `error`) — наступний прогін
скрипта повторить спробу для тих самих книг (ретраюваність через ідемпотентність, не окремий
механізм).

**Немає ресемплінгу/перестиску зображення** — у проєкті немає бібліотеки обробки зображень
(перевірено `package.json`), сам `cover-upload` Edge Function теж лише валідує й пересилає
байти як є. WebP теж не конвертується — `book-covers` bucket дозволяє лише
`image/jpeg`/`image/png` (`allowed_mime_types`, `supabase/schema.sql`), тож і сенсу немає.

## Ідемпотентність

Той самий CSV, запущений двічі з `--apply`, **не створює жодного незапланованого дубліката**:

- Upsert (`Prefer: resolution=merge-duplicates`) за `id` — той самий ефект, що
  `ON CONFLICT (id) DO UPDATE`: повторний запуск оновлює наявні рядки, не дублює.
- Обкладинки **не перезавантажуються за замовчуванням**, якщо `cover_url` у базі вже вказує на
  ВЛАСНЕ сховище (`fetchExistingCoverUrls` перевіряє це ПЕРЕД мережевим викликом) — `--refresh-covers`
  форсує повторне завантаження всіх обкладинок, коли це справді потрібно (наприклад, джерело
  оновило зображення).
- Перевірено НЕ лише читанням коду, а реальним прогоном (`scripts/sync-curated-books.test.js`,
  секція "CLI end-to-end — ідемпотентність"): CLI-скрипт запускається як справжній дочірній
  процес двічі проти локального mock Supabase-сервера — другий прогін дає `created: 0`,
  `updated: N`, `coverReused: N`, той самий один storage-аплоад разом узятих (не два), той самий
  `cover_url` (не новий випадковий UUID).

`is_active=false` — **не видалення**. Рядок лишається в базі, просто прихований з пошуку й
рекомендацій (`CuratedCatalogProvider`'s читання вже фільтрує за цим полем). Скрипт ніколи не
виконує `DELETE`.

## Провенанс без UI-захаращення

`{batchId}-normalized.json` (завжди пишеться, і при dry-run, і при apply, у `--report-dir`) —
повний знімок нормалізованих даних, включно з `coverSourceUrl`, доступний власнику для аудиту
чи діагностики. Ані Search, ані Book Details його не читають чи не показують.

Аудит `Search`/`Book Details` (перевірено читанням реального коду, не припущенням):

- **Search** (`app/(tabs)/search.tsx`'s `ProviderResultRow`/`WorkResultRow`) — уже показує лише
  `coverUrl` (як зображення, не текст), `title`, `authors`, опційний лічильник соцдоказу —
  жодних сирих слагів/URL/булевих полів/мовних кодів/повних описів. Змін не знадобилось.
- **Book Details** (`app/work/[workId].tsx`) — назва/автори/обкладинка/опис (повний текст тут
  доречний) чисті; `is_active`/provenance-URL/слаг ніде не рендеряться. **Але аудит знайшов
  РЕАЛЬНИЙ, окремий від цієї фічі баг**: секція "Видання" (`EditionCard`) показувала
  `edition.language` СИРИМ рядком ("Мова: uk") — на відміну від `format`, що вже йшов через
  `editionFormatLabels`. Це стосується КОЖНОГО видання в застосунку (з будь-якого провайдера,
  не лише кураторського каталогу), і саме той клас "сирого поля в UI", який цей аудит мав
  перевірити — тож мінімальний фікс (`editionLanguageLabels`/`getEditionLanguageLabel`,
  `src/design/i18n-labels.ts`, застосовано в `app/work/[workId].tsx`) зроблено як частина цього
  аудиту, з власним тестом (`src/design/i18n-labels.test.ts`). Мапа — ЧАСТКОВА (`language` —
  вільний рядок від різних провайдерів, не закритий enum, докладніше коментар у самому файлі):
  нерозпізнаний код і далі показується як є (не гірше, ніж було), розпізнаний — людським
  словом.

## CLI

```
node scripts/sync-curated-books.js <file.csv> [--apply] [--refresh-covers]
                                    [--concurrency=6] [--report-dir=data/import-reports]
                                    [--env-file=.env.admin]
# або
npm run catalog:import -- <file.csv> [...ті самі прапорці]
```

- **За замовчуванням — DRY RUN**: жодного запису в Supabase, жодного завантаження обкладинок,
  жодних Supabase-креденшлів не вимагається взагалі — лише parse → validate → normalize →
  deduplicate → звіт про наміри. Потрібен явний `--apply`, щоб щось справді записати.
- `--refresh-covers` — форсує повторне завантаження всіх обкладинок навіть для книг, що вже
  мають власний storage URL.
- `--concurrency=N` (типово 6) — керована паралельність завантаження обкладинок (4-8 —
  рекомендований діапазон, ввічливо до серверів джерела).
- `--report-dir` (типово `data/import-reports/`, у `.gitignore` — локальні артефакти прогону,
  не частина джерела) — куди пишуться звіти й `{batchId}-normalized.json`.
- `--env-file` (типово `.env.admin`) — `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY`; `process.env`
  має пріоритет над файлом (зручно для CI без файлу на диску).

Кожен прогін має унікальний `batchId` (timestamp + короткий UUID) — файли звітів різних
прогонів ніколи не перезаписують одне одного.

## Коди помилок/попереджень

Повний список — `scripts/catalog-import/errorCodes.js`. `severity: 'error'` — рядок НЕ
апсертиться, решта файлу імпортується далі. `severity: 'warning'` — рядок усе одно
імпортується, попередження лише для огляду власником.

| Код | Рівень | Коли |
| --- | --- | --- |
| `INVALID_CSV` / `MISSING_HEADER_COLUMN` | error | Файл не парситься / бракує обов'язкової колонки в header. |
| `MISSING_ID` / `INVALID_ID` | error | Порожній `id` / не відповідає формату `[a-z0-9-]{1,100}` (`curated_book.id` CHECK). |
| `MISSING_TITLE` / `TITLE_TOO_LONG` | error | Порожня назва / довша за 500 символів. |
| `INVALID_ISBN` | error | Хибна контрольна цифра чи довжина. |
| `INVALID_PAGE_COUNT` | error | Не додатне ціле. |
| `INVALID_COVER_URL` | error | Не http(s) або довший за 2000 символів. |
| `DESCRIPTION_TOO_LONG` / `INVALID_LANGUAGE` / `INVALID_BOOLEAN` / `INVALID_UTF8` | error | CHECK-обмеження таблиці або зіпсовані байти. |
| `DUPLICATE_ISBN` | error | Той самий ISBN у різних `id` того самого файлу. |
| `AMBIGUOUS_WORK_MATCH` | error (наразі недосяжний) | Зарезервовано для майбутнього title-based режиму. |
| `DB_UPSERT_FAILED` | error | Supabase відхилив upsert цього конкретного рядка. |
| `COVER_DOWNLOAD_FAILED` / `COVER_HTTP_ERROR` / `COVER_INVALID_IMAGE` / `COVER_TOO_LARGE` / `COVER_UPLOAD_FAILED` | warning | Обкладинка не вдалась — книга однаково імпортується. |
| `DUPLICATE_ID_IN_FILE` | warning | Той самий `id` двічі у файлі — останній рядок перемагає. |
| `NO_GENRES` / `UNKNOWN_GENRE` | warning | Немає жанру / жанр поза `GenreRepository.SEED_GENRES`. |
| `UNKNOWN_PURPOSE` | warning | `purposes` поза `light`/`cry`/`laugh`/`absorbed`. |
| `POTENTIAL_SERIES_METADATA` | warning | Назва містить «Книга N» без явних полів серії (формат їх ще не підтримує) — НЕ вгадується автоматично, лише прапорець для ручної перевірки. |
| `SUSPICIOUS_SHORT_DESCRIPTION` | warning | Опис коротший за 20 символів. |

## Безпека

`SUPABASE_SERVICE_ROLE_KEY` — лише в `.env.admin` (у `.gitignore`, ніколи не комітиться) або
`process.env` довіреного CI-середовища. **Ніколи** не в жодному файлі з префіксом
`EXPO_PUBLIC_` (той інлайниться в клієнтський бандл Expo) і ніколи не в коді застосунку —
пайплайн повністю окремий від `src/`, працює лише через `node scripts/...` з терміналу.
Детальні застереження — `.env.admin.example`.

Мережева ввічливість: кероване паралельне завантаження обкладинок (4-8 воркерів), таймаути на
кожен HTTP-виклик, backoff-ретраї лише на транзієнтні причини (429/5xx), жодного скрейпінгу чи
обходу CAPTCHA — джерело обкладинки або віддає файл нормально, або пропускається.

## Продуктивність (виміряно, не заявлено)

Повний dry run реального `data/curated-books.csv` (2094 рядки, без мережевих викликів — Supabase
не налаштовано в цьому середовищі) — **~0.3с**. `--apply` з реальними мережевими викликами
масштабується лінійно за кількістю НОВИХ/змінених обкладинок (кероване паралельно,
`--concurrency`), не за загальною кількістю рядків — чиста частина пайплайну (parse/validate/
normalize/dedupe) незмінно швидка на порядки більших файлах, бо кожен крок — один прохід по
масиву без вкладених O(n²) порівнянь (дедуплікація — `Map`-пошук, не подвійний цикл).

## Відомі обмеження

- Дедублікація — лише в межах ОДНОГО файлу одного запуску. Якщо два ОКРЕМІ прогони (різні
  файли чи різний час) заявляють той самий ISBN під різними `id`, другий апсерт впаде на
  `curated_book_isbn13_key`/`curated_book_isbn10_key` (`23505 unique_violation`,
  `DB_UPSERT_FAILED` у звіті) — свідомо: перехресно-файлова дедуплікація вимагала б додаткового
  SELECT по ISBN перед кожним upsert, не варте складності для каталогу, що курується вручну
  одним власником.
- Обробка зображень зупиняється на сигнатура+розмір (див. розділ вище) — жодного ресемплінгу.
- `field_provenance` (локальна SQLite-таблиця) лишається невикористаною — цей пайплайн її не
  активує (поза межами ТЗ, таблиця й так не читається жодним репозиторієм).
- Легасі-конвертер позиційного (без header) формату НЕ реалізований — реальний
  `data/curated-books.csv` уже має правильний header, конвертер був би нев тестованим кодом
  без реального застосування.
