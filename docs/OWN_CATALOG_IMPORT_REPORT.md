# OWN_CATALOG_IMPORT_REPORT.md — Фінальний звіт: імпорт власного каталогу книг

## Що зроблено

Побудовано повний, тестований, ідемпотентний CLI-пайплайн імпорту кураторської добірки книг
(`data/curated-books.csv` → `curated_book` у Supabase), який `data/README.md` уже документував,
але якого фактично не існувало в репозиторії (перевірено на самому початку роботи: `scripts/`
не існувало взагалі). Повний опис архітектури, формату, кодів помилок — `docs/OWN_CATALOG_IMPORT.md`;
цей файл — підсумок результату й доказ, що воно працює на реальних даних.

**Це не новий застосунок.** Жодної нової таблиці, RPC, npm-залежності. Ціль (`curated_book`),
сховище обкладинок (`book-covers` bucket), контрольовані словники (`GenreRepository.SEED_GENRES`,
`RecommendationPurpose`) — усе вже існувало; побудовано лише пайплайн, що коректно туди пише.

## Дослідження ПЕРЕД кодом (пріоритет джерел істини)

Перед написанням жодного рядка коду досліджено (у порядку: реальна БД-схема > міграції >
код репозиторіїв > Supabase-схема > наявні імпорт-скрипти > тести > документація):

- `src/lib/csv.ts`/`src/lib/isbn.ts` — наявні pure-функції з задокументованою анти-залежницькою
  політикою; `supabase/functions/isbndb-proxy/isbn.ts` — наявний прецедент навмисної
  cross-runtime дублікації.
- `eslint.config.js` — уже готовий `ignores: [..., 'scripts/**/*.js']` з коментарем, що прямо
  анципує цю фічу.
- `data/curated-books.csv` — РЕАЛЬНІ 2094 рядки проаналізовано (Python) ще до дизайну валідації
  — звідти й походять конкретні перевірки (id > 100 символів, реальний ISBN-конфлікт).
- `supabase/functions/cover-upload/index.ts` — конвенція шляху/заголовків Storage, алгоритм
  `sniffImageType`, ліміт 5 МБ, rate limit (чому пряме `service_role`-завантаження, а не ця
  функція).
- `app/(tabs)/search.tsx`, `app/work/[workId].tsx` — що саме вже рендерить UI (аудит "жодних
  сирих полів").

## Побічний фікс: сирий мовний код на Book Details

Аудит Search/Book Details UI (обов'язковий пункт ТЗ — перевірка, що жодне сире поле імпорту не
просочується в UI) знайшов реальний, окремий від цієї фічі баг: `EditionCard`
(`app/work/[workId].tsx`) показував `edition.language` буквально — "Мова: uk" — для будь-якого
видання в застосунку (з будь-якого провайдера, не лише кураторського каталогу), на відміну від
`format`, що вже йшов через `editionFormatLabels`. Оскільки це саме той клас проблеми, який цей
аудит мав перевірити (і Book Details — його явна ціль), і фікс мінімальний та ізольований —
виправлено: `getEditionLanguageLabel` (`src/design/i18n-labels.ts`) з частковою мапою
найпоширеніших кодів (`uk`/`ukr`/`ukrainian` тощо — джерело розбіжності форматів:
`src/data/providers/ukrainianFilter.ts`, де вже задокументовано, що провайдери повертають
мовний код у різних форматах) і graceful fallback на сире значення для нерозпізнаних кодів (не
гірше, ніж було). Search UI змін не потребував — уже чистий.

## Ідемпотентність — перевірено реальним прогоном, не лише читанням коду

`scripts/sync-curated-books.test.js`, секція "CLI end-to-end — ідемпотентність": реальний
дочірній процес (`node scripts/sync-curated-books.js ... --apply`) запускається ДВІЧІ проти
локального HTTP-сервера, що імітує Supabase PostgREST + Storage. Результат другого прогону
того самого CSV:

- `created: 0`, `updated: 2` (не 2 нових — жодного незапланованого дубліката).
- `coverDownloaded: 0`, `coverReused: 1` — обкладинка НЕ перезавантажується вдруге (skip-by-default).
- Рівно один storage-аплоад РАЗОМ УЗЯТИХ за обидва прогони (не два).
- `cover_url` після другого прогону — той самий рядок, що після першого (не новий випадковий UUID).

Той самий сценарій під час розробки тесту відтворено і вручну (bash, з фоновим mock-сервером) —
підтверджено двічі незалежними способами.

## `--apply` НЕ виконувався

У цьому середовищі немає реальних `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` для продакшн-проєкту
"Полиці" — і не повинно бути: `service_role`-ключ навмисно ніколи не потрапляє в середовище, де
працює агент, лише на пристрій власника (`.env.admin`, у `.gitignore`). Тому реальний запис у
продакшн Supabase **не імітувався і не заявлявся як виконаний** — лише dry run (вище) і
ідемпотентний E2E-тест проти mock-сервера (розділ вище).

**Точна команда для власника, щоб виконати реальний імпорт:**

```bash
# 1. Одноразово: скопіювати .env.admin.example → .env.admin, вписати service_role ключ
cp .env.admin.example .env.admin
# (відредагувати .env.admin — SUPABASE_URL і SUPABASE_SERVICE_ROLE_KEY)

# 2. Спочатку ЗАВЖДИ dry run — перевірити звіт
node scripts/sync-curated-books.js data/curated-books.csv

# 3. Коли звіт виглядає очікувано — записати насправді
node scripts/sync-curated-books.js data/curated-books.csv --apply
```

## Якісні ворота (quality gates)

`npx tsc --noEmit`, `npm test`, `npx eslint . --max-warnings=0` — той самий блок команд, що й
завжди, буде надіслано власнику окремим повідомленням після цього звіту (протокол сесії:
команди завжди даються одним блоком, вивід очікується назад від власника, тут не виконуються
самим агентом, оскільки `node_modules` не встановлено в цьому середовищі).

Натомість, поки `node_modules` недоступний, реальну поведінку кожного нового чистого модуля
самостійно перевірено полегшеними Node-скриптами (без jest, прямий `require`+`assert`) — 42
точкові перевірки, усі пройдені: `dedupe.js`/`normalize.js`/`cover.js`/`supabaseAdmin.js`/
`report.js`/`csv.js`/`isbn.js`/`validate.js`. Сам CLI-скрипт (`sync-curated-books.js`)
перевірено НЕ лише unit-рівнем, а реальним запуском (двічі, з реальним дочірнім процесом і
реальним HTTP-сервером) — розділ "Ідемпотентність" вище. Це не замінює `npm test` (jest дає
офіційний, комітований результат), лише дає впевненість ще до першого реального прогону jest.

## Продуктивність

Повний парсинг+валідація+нормалізація+дедуплікація 2094 реальних рядків — **~0.3 секунди**, без
жодного мережевого виклику (Supabase не налаштовано в цьому середовищі). Це навмисно НЕ
включає мережеву частину (`--apply` з реальними завантаженнями обкладинок) — та частина
масштабується лінійно за кількістю НОВИХ/змінених обкладинок, керовано паралельно
(`--concurrency`, типово 6), не за загальною кількістю рядків. Немає жодного O(n²) кроку в чистій
частині пайплайну — дедуплікація й пошук наявних обкладинок працюють через `Map`/пакетний
`id in.(...)` запит, не вкладені цикли.

## Відповідність головній умові прийняття

Пайплайн не знає нічого специфічного про сьогоднішні 2094 рядки — жодного хардкоду книги в
коді, жодного файлу на книгу. Додавання наступних 10 000 рядків у `curated-books.csv` (чи
цілком новий CSV-файл, `data/catalog-import-template.csv` як заготовка) потребує НУЛЬ змін коду
застосунку — лише новий/оновлений CSV і той самий `node scripts/sync-curated-books.js ... --apply`.
Звичайний користувацький Search і Book Details й далі бачитимуть те саме: обкладинка → назва →
автор → компактні метадані, жодних технічних деталей імпорту.
