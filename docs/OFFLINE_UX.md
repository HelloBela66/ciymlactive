# OFFLINE_UX.md — Offline UX (Фаза 20)

POLYTSIA V1.6.1, Фаза 20 (OFFLINE UX). Той самий "фіксує рішення, яке інакше довелось би
пояснювати заново" документ, що й `docs/CALENDAR_2_0.md`/`docs/HOME_REFINEMENT.md`/
`docs/PROGRESSIVE_ONBOARDING.md`.

## Завдання (буквально)

"Network-dependent екрани (Search) повинні пояснювати offline state окремо від 'нічого не
знайдено'. Перевірити Expo-сумісний network package перед додаванням залежності."

## Контекст

`docs/LOCAL_FIRST.md` §"Offline-індикатор" уже задокументував намір ще до цієї фази:
"`NetInfo`-подібний стан (через `expo-network`, за потреби) показує делікатний inline-banner
лише на екрані пошуку/сканера, ніколи глобальний блокуючий overlay". Аудит (§39.1, CODE
VERIFIED) підтвердив: жодного імпорту `expo-network`/`NetInfo` в усьому репозиторії до цієї
фази — задум був, підключення не було. Ця фаза, як і Фаза 19, добудовує вже задумане, а не
вигадує новий дизайн з нуля.

`src/features/search/useProviderSearch.ts` (власний doc-коментар файлу) підтверджує: кожен
провайдер (спільний каталог, Google Books, ISBNdb) сам ковтає мережеві помилки й повертає `[]`
— тобто React Query-шний `isError` НЕ є придатним сигналом для відрізнення "офлайн" від
"нічого не знайдено". Це й було головною технічною перешкодою фази: потрібна незалежна
перевірка з'єднання, а не інспекція стану запиту.

## Архітектурні рішення

### Пакет: `expo-network`, не `@react-native-community/netinfo`

`package.json` містить виключно `expo-*` залежності (жодного `@react-native-community/*`
пакета). `expo-network` — перший-party Expo-пакет, уже входить в Expo Go, не потребує
нативного лінкування чи конфіг-плагіна — той самий підхід, що й решта залежностей. Встановлено
командою `npx expo install expo-network` (не хардкоджена версія вручну) — саме так Expo CLI
резолвить SDK-сумісну версію, що прямо відповідає вимозі ТЗ "перевірити Expo-сумісний network
package перед додаванням залежності".

### `useIsOffline` (`src/lib/useIsOffline.ts`)

Тонка обгортка над `Network.useNetworkState()`: `isConnected === false ||
isInternetReachable === false`.

- **Перевіряється і `isInternetReachable`, не лише `isConnected`** — Wi-Fi без реального
  інтернету (капітал-портал готелю/кафе) лишає `isConnected === true`, хоча жоден запит до
  Google Books/ISBNdb/Supabase насправді не пройде. Голий `isConnected` пропустив би цей
  реалістичний сценарій.
- **Оптимістичний дефолт, доки стан не підтверджено** — обидва поля SDK документує як можливо
  `undefined` до першої реальної перевірки; хук у цьому вікні НЕ вважає користувача офлайн (той
  самий "не показуй новий стан, доки не підтверджено" принцип, що й `isLibraryEmpty`/
  `useOnboardingHint`, Фази 17/18) — інакше кожен мережевий екран на частку секунди хибно
  блимнув би офлайн-банером при кожному відкритті.

### Спільний вигляд: `OfflineNotice` (`src/components/ui/OfflineNotice.tsx`)

Презентаційний компонент (`Card` + іконка `cloud-offline-outline` + повідомлення) — один
спільний вигляд для обох мережезалежних поверхонь, а не дублювання розмітки. `docs/
LOCAL_FIRST.md` явно вимагав "делікатний inline-banner… ніколи глобальний блокуючий overlay"
— саме тому це `Card` усередині наявного потоку екрана, а не модалка/оверлей.

### Пошук (`app/(tabs)/search.tsx`)

`isOffline` гейтить усі чотири виклики `useProviderSearch` (`enabled: !isOffline`, разом із
наявними умовами для ISBNdb) — офлайн не просто ховає результат, а й не витрачає марно виклик
на провайдера, що все одно поверне `[]`. У режимі "Каталог" під час пошуку: офлайн → один
`OfflineNotice` замість чотирьох секцій результатів; онлайн — поведінка без змін.

### Сканер ISBN (`app/isbn-scan.tsx`)

Новий статус `'offline'` у `ScanStatus`. Перевірка локальної БД (`localEdition`) лишається
ПЕРЕД офлайн-коротким замиканням — видання, уже наявне локально, і так знаходиться без мережі,
офлайн не повинен блокувати цей шлях. Лише після нього, перед зверненням до `SharedCatalog
Provider.lookupByISBN` (мережевий виклик), стоїть `if (isOffline) { setStatus('offline');
return; }`.

Офлайн-повідомлення НЕ пропонує кнопку "Шукати в Google" (наявну в `not_found`-блоці) — вона
теж потребує мережі й була б робочою лише про людське око. Пропонує "Спробувати сканувати ще
раз" і "Додати вручну" (єдиний шлях, що реально працює офлайн).

## Свідомо НЕ зроблено

- **Жодної mutation/retry-черги.** `docs/V1_6_FULL_AUDIT_REPORT.md` (§39) прямо фіксує
  відсутність retry-queue як **свідоме архітектурне рішення V1**, а не прогалину: застосунок
  локально-перший, усі мутації (сесії/нотатки/оцінки/полиці) записуються в SQLite миттєво й без
  мережі — мережа потрібна лише для (M7) пошуку метаданих зовнішніх провайдерів. Немає що
  ставити в чергу.
- **Жодного глобального offline-індикатора** (банер на кожному екрані, іконка в шапці) — лише
  дві мережезалежні поверхні (пошук, сканер) отримують `OfflineNotice`, точно як задокументовано
  в `docs/LOCAL_FIRST.md` до цієї фази.
- Локальний пошук по вже завантаженій бібліотеці (режим "Моя бібліотека" на екрані пошуку) не
  чіпається — він і так офлайн-стійкий (SQLite), `isOffline` там не використовується.
