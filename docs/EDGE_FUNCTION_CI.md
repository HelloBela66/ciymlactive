# EDGE_FUNCTION_CI.md — Edge Function CI + npm audit (Фаза 25)

POLYTSIA V1.6.1, Фаза 25 (EDGE FUNCTION CI + NPM AUDIT). Той самий "фіксує рішення, яке інакше
довелось би пояснювати заново" документ, що й `docs/PERFORMANCE_AUDIT.md`/
`docs/HAPTICS_CLEANUP.md`.

## Завдання (буквально)

"Окремий CI job для Deno/Supabase Edge Functions (typecheck, lint, shared modules), без
конфлікту з Node CI. Запустити npm audit (без --force), задокументувати findings."

Дві незалежні частини.

## 1. Edge Function CI (окремий job)

### Звідки ця прогалина

`docs/V1_6_FULL_AUDIT_REPORT.md`, розділ 32 — CODE VERIFIED знахідка: `tsconfig.json` (`exclude:
["node_modules", "supabase/functions"]`) і `eslint.config.js` (`ignores: [...,
'supabase/functions/**', ...]`) обидва СВІДОМО виключають `supabase/functions/**` — правильне
рішення саме по собі (Deno-рантайм, глобал `Deno`, імпорти з явним `.ts`, несумісний синтаксис
із звичайним tsc/ESLint-проєктом застосунку), але наслідок — 5 файлів
(`_shared/cors.ts`, `_shared/rateLimit.ts`, `isbndb-proxy/index.ts`, `isbndb-proxy/isbn.ts`,
`cover-upload/index.ts`, і на момент цієї фази ще й `google-books-proxy/index.ts` — 6 файлів
разом) НІКОЛИ не перевірялись жодним автоматичним інструментом на жодному push/PR. Аудит
дослівно рекомендує "додати окремий Deno-крок (`deno check`/`deno test` через Supabase CLI чи
прямий `denoland/setup-deno` action) у CI" (розділ 32, кінець).

### Чому ОКРЕМИЙ job, а не крок усередині `ci`

`.github/workflows/ci.yml` тепер має два jobs: `ci` (Node/tsc/ESLint/Jest, як і раніше) і новий
`edge-functions` (Deno). Обидва запускаються паралельно на одному тригері (`push`/
`pull_request` у `main`), кожен на власному `runs-on: ubuntu-latest`-раннері. Окремий job — не
лише "чистіше", а й буквально те, що вимагає ТЗ ("без конфлікту з Node CI"): різний тулчейн
(Deno CLI проти Node/tsc/ESLint) в одному job означав би або встановлення обох рантаймів на
одному раннері (зайва залежність між кроками, повільніше — Deno-крок чекав би на весь Node
install/test навіть якщо `supabase/functions/**` взагалі не змінювався в цьому push), або
ризик, що якийсь майбутній крок одного рантайму випадково торкнеться файлів іншого. Окремий
job усуває обидва ризики структурно, а не домовленістю "просто не чіпати".

### Що саме перевіряється

- `deno check supabase/functions` — typecheck усіх `*.ts` у теці, включно з `_shared/*.ts`
  ("shared modules" з ТЗ буквально) — не лише трьох entry-point `index.ts`. Передача директорії,
  а не по одному файлу: `_shared/cors.ts`/`_shared/rateLimit.ts` не мають власного
  `Deno.serve`-виклику, тож не є "entry point" самі по собі, але кожен реально імпортується
  мінімум одним із трьох index.ts (перевірено `grep` по всій теці — жодного "мертвого", не
  імпортованого ніким файлу немає), тож транзитивно вже покриті непрямо; пряма перевірка всієї
  директорії явно покриває їх і напряму, а не лише як побічний ефект чужого імпорту (важливо на
  випадок майбутнього shared-модуля, який хтось додасть без негайного імпортера).
- `deno lint supabase/functions` — той самий принцип, уся тека одразу.
- `deno test` — СВІДОМО НЕ додано. На момент цієї фази `supabase/functions/**` не має ЖОДНОГО
  `*.test.ts` файлу (перевірено — `find supabase/functions -name '*.test.ts'` порожньо). Сам
  ТЗ цієї фази явно називає лише "typecheck, lint, shared modules" — не "тести" — і не вимагає
  написання нових тестів для Edge Functions як частину цієї фази. Додавання `deno test` кроку
  без жодного тестового файлу або одразу падало б ("error: no test modules found"), або
  вимагало б `continue-on-error: true`, що назавжди приховувало б майбутню реальну відсутність
  тестів під зеленим статусом — жоден із варіантів не кращий за просто не додавати крок, якого
  ще нема чим наповнити.

### Чому блокуючий (не advisory), на відміну від `expo-doctor`/`npm audit`

`deno check`/`deno lint` перевіряють РЕАЛЬНИЙ код репозиторію (типи, синтаксис, лінт-правила) —
той самий клас перевірки, що й `tsc --noEmit`/`eslint` для Node-частини (блокуючі кроки job
`ci`), а не зовнішній стан (мережа для `expo-doctor`, npm registry CVE-база для `npm audit`),
тож той самий рівень суворості логічно застосовний. На момент написання цього документа обидва
кроки мали б пройти чисто (Edge Functions уже задеплоєні й реально працюють у продакшні
— `docs/SECURITY.md`, розділи "Оновлення" — увесь код перевірено вручну читанням перед цією
фазою: жодних Node-специфічних API (`require`/`process.*`/`Buffer`/`__dirname`), жодних
`: any`, лише relative `.ts`-імпорти без зовнішніх залежностей — `deno check` не потребує
`import_map.json`/мережевого резолвінгу зовнішніх пакетів узагалі).

### Версія Deno

`deno-version: v2.x` (той самий "остання стабільна в мажорній лінії" підхід, що й `node-version:
'22'` вище — floating у межах мажорної версії, не фіксований патч, якого власник продукту потім
мусив би вручну оновлювати). Supabase Edge Runtime сумісний із Deno 2.x.

### Не перевірено локально (сесійне обмеження)

Ні `deno`, ні `denoland/setup-deno`, ні `deno.land` не доступні з мережі цієї (хмарної) сесії
(перевірено прямою спробою — `curl https://deno.land/install.sh` повертає `403` від
проксі-політики середовища, той самий клас обмеження, що й для `npm audit` нижче). Синтаксис
`deno check`/`deno lint` (стандартні, стабільні CLI-команди, обидві приймають шлях до
директорії й рекурсивно перевіряють усі `.ts`/`.js`-файли під ним) не міг бути dry-run
перевірений у цій сесії — той самий клас обмеження, що й для CI в усіх попередніх фазах: реальна
верифікація — сам прогін GitHub Actions після пушу, а не локальний dry-run.

## 2. npm audit

### Спроба виконати в цій сесії — заблокована мережевою політикою

`npm audit` (і, для повноти, `npm audit --json`) запущено проти РЕАЛЬНОГО `package.json`/
`package-lock.json` репозиторію в цій сесії. Результат — не список вразливостей, а мережева
помилка:

```
npm warn audit 403 Forbidden - POST https://registry.npmjs.org/-/npm/v1/security/audits/quick
npm error audit endpoint returned an error
```

JSON-відповідь проксі середовища прямо називає причину: `"x-deny-reason": ["host_not_allowed"]`,
`"body": "Host not in allowlist: registry.npmjs.org."`. Це НЕ те саме обмеження, що описане в
`docs/V1_6_FULL_AUDIT_REPORT.md` (розділ 34) — той аудит взагалі не мав `Bash`/мережевих
інструментів у своєму завданні. Ця сесія Bash МАЄ, але мережевий allowlist цього конкретного
хмарного середовища не включає `registry.npmjs.org` — інше, вужче обмеження з тим самим
практичним наслідком: жодна сесія AI-агента (ні аудит, ні ця фаза) ще не бачила реального
виводу `npm audit` для цього проєкту.

### Що зроблено замість прямого запуску

Додано крок `npm audit --audit-level=high` у job `ci` (`.github/workflows/ci.yml`) — та сама
позиція в pipeline, що й `expo-doctor`, з тим самим `continue-on-error: true`. GitHub Actions
runner (на відміну від цієї сесії) має звичайний мережевий доступ до `registry.npmjs.org` —
тож щойно ця фаза буде задеплоєна й CI відпрацює на реальному push, цей крок ВПЕРШЕ реально
виконає перевірку, а точний список CVE (якщо є) буде видно в логах того прогону.

`--audit-level=high` (не дефолтний "усе, включно з low") — свідомий вибір, синхронний з тим,
що вже відомо: власник продукту раніше бачив "19 moderate severity vulnerabilities" при
звичайному `npm install` на своїй машині (`docs/SECURITY.md`, розділ 3) — типовий шум
транзитивних dev-залежностей для будь-якого Expo/React Native проєкту такого розміру. Валити
щоденний pipeline через low/moderate, які часто взагалі не зачіпають рантайм застосунку
(dev-only tooling), означало б або постійно ігнорований червоний статус, або постійні
`continue-on-error`-винятки — `--audit-level=high` фільтрує шум на рівні самої команди, лишаючи
видимими лише high/critical, ті, що справді заслуговують на увагу першими.

`continue-on-error: true` — не тому, що high/critical неважливі, а тому, що рішення "чи мусить
знайдена вразливість валити collaborators' pipeline" — продуктове рішення власника продукту
(`npm audit fix` може бути breaking-зміною, яку не можна застосувати наосліп у CI), не технічне
рішення цієї фази. Той самий компроміс, що аудит сам явно назвав прийнятним (розділ 34, п.3:
"можливо, `continue-on-error: true` ... якщо власник продукту не хоче, щоб сама наявність
low/moderate вразливості валила pipeline").

### GitHub Dependabot alerts — НЕ увімкнено цією фазою

Аудит (розділ 34, п.2) також рекомендує увімкнути GitHub Dependabot alerts/security updates
(Settings → Security → Code security). Це — зміна налаштувань самого GitHub-репозиторію (не
файл у git), яку не можна виконати з коду цієї фази: вимагає доступу до GitHub Settings UI/API
з правами власника репозиторію. Задокументовано тут як OWNER ACTION REQUIRED (той самий клас
запису, що вже є в `docs/CI.md`/`docs/TESTING.md` для першого `git init`/`push`), не як
пропущений крок цієї фази.

## Перший реальний прогін (CI run #80) — знайдена й виправлена справжня помилка

Точно та ситуація, яку розділ вище явно передбачав ("реальна верифікація — сам прогін GitHub
Actions після пушу, а не локальний dry-run"): перший же реальний прогін нового job
`edge-functions` (CI run #80, одразу після коміту Фази 25) НЕ пройшов. `deno check
supabase/functions` впав з `TS2769: No overload matches this call` на
`supabase/functions/cover-upload/index.ts:185` — виклик `fetch(..., { body })`, де `body` мав
тип `Uint8Array<ArrayBufferLike>` (непараметризований `Uint8Array`), який не збігається з жодним
`BodyInit`-оверлоадом `fetch` у сучасних DOM-типах TypeScript (`Uint8Array<ArrayBufferLike>`
теоретично включає й `SharedArrayBuffer`, а `BodyInit`-оверлоади очікують конкретніший
`Uint8Array<ArrayBuffer>`).

**Виправлення:** сигнатура `readRequestBodyWithLimit` у `cover-upload/index.ts` уточнена на
`Promise<Uint8Array<ArrayBuffer> | 'too_large'>` — обидва її фактичні `return`-шляхи й без того
завжди створюють `Uint8Array` над справжнім `ArrayBuffer` (`new Uint8Array(await
req.arrayBuffer())`, `new Uint8Array(total)`), тож це виправлення виключно на рівні типів,
жодної зміни рантайм-поведінки. Корінь і сама відповідність виправлення підтверджені локально
мінімальним репро-файлом через звичайний `tsc --strict --lib dom --noEmit` (`deno` сам
недоступний з мережі цієї сесії, як і описано вище) — та сама помилка відтворюється без
виправлення й зникає з ним.

Це саме по собі підтверджує сенс усієї цієї фази: `cover-upload/index.ts` існував і був
задеплоєний у продакшн уже до цієї фази з цією помилкою типів, і жоден інструмент її ніколи не
бачив (Deno рантайм у продакшні транспілює/виконує `.ts` без попередньої `deno check`-перевірки
типів — помилка типів сама по собі не завадила б функції працювати, але могла б замаскувати
майбутню реальну регресію в тому самому місці).

## Свідомо НЕ зроблено

- **`deno test` крок** — докладніше вище, §"Що саме перевіряється": жодного тестового файлу ще
  немає, ТЗ фази не вимагає його писати.
- **Фіксація точного списку CVE в `docs/SECURITY.md`** — не можна задокументувати те, чого ще
  не бачено; `docs/SECURITY.md` (розділи 3 і 4) оновлено з описом ЩО зроблено (крок у CI) і ЯК
  саме побачити реальний результат (перший прогін CI після пушу цієї фази), а не з вигаданими
  числами.
- **Увімкнення GitHub Dependabot alerts** — докладніше вище, §"GitHub Dependabot alerts".
- **Зміна суворості `deno check`/`deno lint` (наприклад, конкретних lint-правил Deno)** — обрано
  стандартну конфігурацію Deno CLI без `deno.json`/кастомних правил: увесь наявний код уже
  написаний у стилі, який (за ручною перевіркою перед цією фазою) не порушує жодного
  стандартного правила Deno lint — додавати конфігурацію заради коду, який і без неї пройде,
  було б передчасною складністю.
