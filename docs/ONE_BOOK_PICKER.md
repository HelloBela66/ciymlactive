# ONE_BOOK_PICKER.md — «Обери мені книгу» (Фаза 16)

POLYTSIA V1.6, Фаза 16 (ONE BOOK PICKER). Той самий "фіксує рішення, яке інакше довелось би
пояснювати заново" документ, що й `docs/READING_FINGERPRINT.md`/`docs/READING_PROFILE.md`.

## Мета й відмінність від «Що почитати завтра?»

ТЗ Фази 16: «Покращ поточний «Що почитати завтра?». Не видаляй existing recommendation logic
без причини.» — прочитано буквально: `src/lib/tomorrowRecommendation.ts`/
`src/features/tomorrow/useTomorrowRecommendation.ts`/`app/tomorrow.tsx` лишаються без змін.
«Обери мені книгу» — ОКРЕМА, паралельна фіча з принципово іншим data source:

| | «Що почитати завтра?» | «Обери мені книгу» |
|---|---|---|
| Звідки кандидати | Google Books / курований каталог (ЗОВНІ) | Бібліотека користувача (`user_book`, переважно TBR) |
| Що повертає | Книгу, якої ще НЕМАЄ в бібліотеці | Книгу, яка вже Є в бібліотеці |
| Дія над результатом | «Додати в бібліотеку» (import flow) | «Обрати цю» → Book Details |

Через це `src/lib/onePicker.ts` — новий, незалежний файл (не розширення
`tomorrowRecommendation.ts`): фільтри й кандидати мають різну форму, спільної логіки для
перевикористання по суті немає. Перевикористано лише те, що вже є "спільним словником", а не
приватним хелпером однієї фічі: `RecommendationPurpose`/`PURPOSE_KEYWORDS` (той самий набір
"настроїв" в обох пікерах) і `FALLBACK_PAGES_PER_MINUTE` з `readingPace.ts`.

## Архітектура

- `src/lib/onePicker.ts` — чисті функції: фільтрація (`filterCandidates`), м'яке ранжування за
  настроєм+близькістю сторінок (`rankCandidates`), випадковий вибір серед топ-5
  (`pickCandidate` — той самий підхід, що й `tomorrowRecommendation.ts#pickCandidate`), оцінка
  часу читання (`estimateMinutesToRead`), статус серії (`formatSeriesStatus`), пояснення вибору
  (`buildPickExplanation`).
- `src/features/onePicker/useOnePicker.ts` — `useMutation` (не `useQuery`, той самий підхід, що
  й `useTomorrowRecommendation`: результат недетермінований і не повинен кешуватись як
  стабільне значення для тих самих фільтрів). Збір сирих даних (`UserBookRepository.
  listByStatus`, пакетні `GenreRepository.listByWorkIds`/`SeriesRepository.
  listWorkIdsInSeries`/`OwnedBookRepository.listOwnedEditionIds`), виклик чистих функцій.
- `app/one-book-picker.tsx` — пікер фільтрів зверху, ОДНА картка результату знизу (ТЗ: "Не
  20"). CTA «Обрати цю» → Book Details (`/work/[workId]`, користувач сам вирішує, коли почати
  сесію звідти); secondary «Іншу» → повторний вибір, виключаючи вже показані книги цього сеансу
  (клієнтський `Set`, без нової таблиці — пул кандидатів тут маленький і локальний, на відміну
  від зовнішнього пошуку `tomorrowRecommendation.ts`, якому потрібна персистентна shown-history).
- Home: новий `OnePickerEntryPointCard` (`app/(tabs)/index.tsx`) поруч із
  `TomorrowEntryPointCard`, той самий візуальний патерн.

## Фільтри

1. **Скільки часу є** — той самий `TIME_BUDGET_OPTIONS`/`estimatePageBudget`, що й «Що
   почитати завтра?»: пресет часу → цільова кількість сторінок (через rolling pace
   користувача, `readingPace.ts`). М'який сигнал ранжування (близькість `pageCount` до цілі),
   НЕ жорсткий фільтр — книга з іншою довжиною не виключається, лише йде нижче в списку.
2. **Настрій** — ті самі 4 значення `RecommendationPurpose`, що й «Що почитати завтра?» (той
   самий словник для консистентності), але тут — М'ЯКИЙ сигнал: `matchesDesiredMood` шукає
   `PURPOSE_KEYWORDS` серед жанрів+опису твору. Навмисно не жорсткий фільтр: у книги в
   бібліотеці рідко є надійний "тег настрою", жорсткий фільтр за такою слабкою ознакою легко
   лишив би порожній результат. Збіг настрою пріоритетніший за близькість сторінок у
   `rankCandidates` — книга, що збігається настроєм, завжди йде вище книги без збігу.
3. **Максимальна довжина** — ЖОРСТКИЙ фільтр (кілька пресетів: 300/500/800/без обмежень).
   Книги з невідомою довжиною (`pageCount === null`) НЕ виключаються — тиха деградація,
   той самий принцип, що й усюди в застосунку.
4. **Серія** — будь-яка / лише окремі історії / лише частини серій
   (`SeriesRepository.listWorkIdsInSeries`, пакетна перевірка членства, додана в Фазі 15 для
   бейджа «Читає серіями» й перевикористана тут).
5. **Статус у бібліотеці** — лише «Хочу прочитати» (`want_to_read`) або ширше: «Хочу
   прочитати»+«На паузі»+«Не дочитав» (свідомо БЕЗ `reading`/`rereading` — книгу, яку й так уже
   читаєш, підбирати нема сенсу — і без `finished`).
6. **Володіння** — будь-яка книга бібліотеки, або лише позначені фізично своїми
   (`OwnedBookRepository.listOwnedEditionIds`, новий пакетний метод — "я маю цю книгу фізично"
   окремо від reading-статусу, `docs/DATABASE.md`).

## Пояснення вибору (EXPLANATION)

ТЗ: "Recommendation повинен бути explainable... Не вигадуй attributes, яких немає в metadata."
`buildPickExplanation` збирає причини ЛИШЕ з реальних, уже порахованих фактів (обраний часовий
пресет, чи збігся настрій, чи книга позначена своєю, який фільтр серії/жанру застосований) —
жодна причина не вигадується й не залежить від тексту, якого немає в даних. Не більше
`MAX_EXPLANATION_REASONS = 3` причин в одному реченні (довший список гірше читається).
