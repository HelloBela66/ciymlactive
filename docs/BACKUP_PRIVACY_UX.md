# BACKUP_PRIVACY_UX.md — Backup privacy UX (Фаза 21)

POLYTSIA V1.6.1, Фаза 21 (BACKUP PRIVACY UX). Той самий "фіксує рішення, яке інакше довелось би
пояснювати заново" документ, що й `docs/OFFLINE_UX.md`/`docs/CALENDAR_2_0.md`.

## Завдання (буквально)

"Warning перед external share бекапу (приватні записи, не зашифровано). Без автоматичного
encryption у цьому milestone."

## Контекст

Аудит (`docs/V1_6_FULL_AUDIT_REPORT.md`, розділ 59, P1) зафіксував: "Резервна копія — повний,
нешифрований JSON з усіма приватними нотатками/цитатами/DNF-причинами/pre-reading
рефлексіями, який `expo-sharing` дозволяє відправити будь-яким каналом (месенджер, email,
хмарний диск) без попередження про вміст". Той самий ризик окремо названо і в технічному
реєстрі (розділ 58, T6): немає навіть опційного шару шифрування/пароля.

`docs/BACKUP_FORMAT.md` (§Формат JSON-експорту) підтверджує повний перелік таблиць у файлі —
включно з `note`/`quote`/`dnf_reflection`/`pre_reading_reflection`/`book_memory` — те, що
людина, найімовірніше, вважала б особистим, не просто метаданими бібліотеки.

## Архітектурне рішення

### Попередження, не шифрування

ТЗ цієї фази прямо обмежує скоуп: "без автоматичного encryption у цьому milestone". Це свідомо
UX-рішення (попередити людину ПЕРЕД тим, як вона сама віддасть файл кудись назовні), а не
технічний захист самого файлу — файл на диску пристрою лишається звичайним plaintext JSON, як і
до цієї фази (`docs/BACKUP_FORMAT.md` не змінено).

### Де саме показується попередження

`app/backup.tsx`, `handleExport` — `Alert.alert` (той самий нативний системний діалог, що вже
використовує ця сторінка для restore-підтвердження, а не кастомна модалка) з'являється ПІСЛЯ
натискання "Створити й поділитися", АЛЕ ПЕРЕД фактичним викликом `useExportBackup` (а отже й
перед `writeAndShareBackupFile`/`Sharing.shareAsync` усередині нього). Дві кнопки: "Скасувати"
(нічого не відбувається, файл навіть не пишеться на диск) і "Створити й поділитися"
(продовжує вже наявний потік запису+"Поділитися" без змін).

**Чому саме тут, а не раніше/пізніше в потоці:**
- НЕ на самому екрані статично (наприклад, банер під заголовком картки) — попередження, яке
  бачать щоразу при вході на екран backup, а не саме перед реальною дією поширення файлу,
  швидко перетворюється на "сліпу пляму", яку більше не читають (той самий принцип, що й
  "делікатний, не глобальний" підхід з `docs/OFFLINE_UX.md`, лише навпаки — тут навпаки
  потрібна саме конкретна точка перед конкретною дією, а не постійний фоновий натяк).
- НЕ після запису файлу на диск, перед самим `Sharing.shareAsync` (тобто не всередині
  `writeAndShareBackupFile`) — `src/lib/backupFile.ts` навмисно не знає про UI/`Alert`
  (той самий поділ, що й у `src/lib/notifications.ts` — файлова/нативна логіка окремо від
  екранної), і сам запис файлу на диск пристрою (без подальшого поширення) не становить
  ризику — ризик виникає рівно в кроці "піти кудись назовні пристрою".

### Чому лише JSON-бекап, не CSV-експорт

`src/features/library-io/libraryCsvExport.ts` (`buildLibraryCsv`) свідомо не включає жодного
поля з нотаток/цитат/DNF-причин/pre-reading рефлексій — лише проекцію метаданих бібліотеки
(назва/автори/статус/оцінка/жанри/полиці/видавництво/рік/сторінки/ISBN/мова/формат/дати) —
той самий перелік, що й `HEADER`-константа файлу. Рейтинг сам по собі — не той рівень
приватності, що DNF-причина чи текст нотатки. Попередження додано лише до кнопки "Створити й
поділитися" картки JSON-бекапу, кнопка CSV-експорту лишається без змін.

### Чому не зачепило автоматичний бекап

`useAutoBackup.ts`/`autoBackup.ts` — тихий локальний бекап у власні файли застосунку, БЕЗ
жодного виклику `Sharing.shareAsync` (файл лишається на пристрої, ніколи не покидає
застосунок сам по собі — те саме підтверджує текст картки "Автоматичний бекап" на екрані:
"Нічого нікуди не надсилається"). ТЗ цієї фази явно про "external share" — авто-бекап не
поширює файл нікуди, тож попереджати нема про що.

## Свідомо НЕ зроблено

- **Жодного шифрування/пароля бекапу** — прямо виключено ТЗ цієї фази ("без автоматичного
  encryption у цьому milestone"); лишається продуктовим боргом (аудит, T6/P1) для майбутнього
  milestone.
- **Жодного "не показувати знову" перемикача** для цього попередження — ТЗ описує
  попередження, а не одноразову підказку (на відміну від `docs/PROGRESSIVE_ONBOARDING.md`,
  де саме одноразовість — явна вимога); "точка неповернення" (реальний зовнішній канал
  поширення приватних даних) виправдовує показ щоразу, той самий підхід, що й restore-
  підтвердження на цьому самому екрані (п.35 ТЗ — "завжди, без винятків").
- **Жоден перелік конкретного вмісту файлу** (наприклад, точні числа "12 нотаток, 3 DNF-
  причини") у самому діалозі — на відміну від restore-підтвердження, де конкретні числа
  доречні (users порівнює з очікуваним станом бібліотеки), тут мета — застерегти про КЛАС
  вмісту (особисті записи), не показати статистику; підрахунок конкретних приватних записів
  заради самого попередження — зайва робота поза скоупом ТЗ.
