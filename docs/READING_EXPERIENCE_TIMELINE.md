# READING_EXPERIENCE_TIMELINE.md — «Як читалася ця книга»

POLYTSIA V1.6, Фаза 7. Цей документ фіксує точну поведінку фічі, щоб вона не змінювалась
випадково в майбутніх фазах (той самий підхід, що й `docs/BOOK_CAPSULES.md`/`docs/RECALL.md`/
`docs/BEFORE_AFTER.md`). На відміну від попередніх фаз V1.6, ця — суто агрегація й нова
візуалізація вже наявних даних: жодної нової таблиці, колонки чи мутації.

## Мета

ТЗ Фази 7 прямо застерігає: "Поточний `reading_experience` вже існує. Не створюй нову duplicate
field. Агрегуй reading experience по sessions." Поле `reading_session.reading_experience` (ТЗ
V1.5 Фази 9 — "Як читалося?", кожна сесія окремо) досі жило лише в списку сесій Book Details.
Ця фаза збирає його по всій книзі в одну горизонтальну шкалу на Book Memory — щоб побачити
форму читацького досвіду цілої книги одним поглядом ("Легко → Захопливо → Напружено → …"), а не
гортати сесію за сесією.

## Точка входу

Секція «Як читалася ця книга» на `app/memory/[workId].tsx` (Book Memory), одразу над шкалою
записів щоденника (`JournalTimeline`) — обидві шкали ділять ту саму позицію 0-100% книги, тож
навмисно стоять поруч. Рендериться лише коли сесій достатньо для чесної шкали (§Замало даних
нижче); немає окремого порожнього стану з поясненням — блок просто ще не з'явився для нової
книги, той самий підхід, що й `JournalTimeline` без жодного позиціонованого запису.

## Дані

Жодної нової таблиці/колонки. Джерело — ті самі завершені сесії, що вже повертає
`ReadingSessionRepository.listByUserBookId` (той самий хук `useReadingHistory`, який уже
використовував цей екран для статистики книги, `computeBookStats`). Кожна сесія стає одним
маркером шкали:

- **позиція** — `endPage` сесії (скільки прочитано УЖЕ ПІСЛЯ неї) відносно `pageCount` видання,
  тим самим `computeProgressPercent`, що й `JournalTimeline`/швидкий запис щоденника;
- **стан** — `reading_experience` сесії (`ReadingExperienceId`, `src/design/readingExperience.ts`,
  5 фіксованих значень), або "без позначки", якщо сесія завершилась без відповіді.

## Якщо `pageCount` невідомий

ТЗ: "Якщо session не має progress — використовуй chronological position." На практиці завершена
сесія завжди МАЄ сторінку (`endPage` завжди проставляє `ReadingSessionRepository.finish`) —
бракувати може лише `pageCount` самого видання (провайдер не дав даних). У такому разі ВСІ
маркери шкали цієї книги рівномірно розподіляються за хронологією (перша сесія — 0%, остання —
100%, решта — порівну між ними), а не лише ті, кому бракує позиції: змішування "справжнього"
прогресу для одних сесій і порядкового номера для інших спотворило б відстані між точками, ніби
вони щось означають.

## Замало даних

ТЗ: "Якщо даних мало (<2–3 sessions) — не показуй misleading chart." Поріг — рівно 3 завершені
сесії (`MIN_SESSIONS_FOR_READING_EXPERIENCE_TIMELINE`, `src/lib/readingExperienceTimeline.ts`):
дві точки на шкалі — це просто відрізок, жодної форми читання ще не видно. Нижче порогу блок не
рендериться зовсім (не "0 маркерів", а `null`), той самий тихий підхід, що й `JournalTimeline`.

## Візуалізація

ТЗ прямо забороняє emoji як ЄДИНИЙ visual encoding. Кожен стан розрізняється ФОРМОЮ іконки, не
кольором — палітра застосунку свідомо нейтральна (`docs/ARCHITECTURE.md` розділ 6, той самий
принцип, що й категорії `JournalTimeline`): сонце (Легко), полум'я (Захопливо), листок (Спокійно),
пульс (Напружено), стрілка вгору (Важко); сесія без позначки — нейтральне коло. Тап по маркеру
показує текстовий підпис під шкалою (дата + стан) — ТЗ: "markers + labels/tooltips", не лише
іконка сама по собі; для screen reader підпис доступний одразу через `accessibilityLabel`,
незалежно від тапу.

## Відомі обмеження (V1.6)

- Маркери не кластеризуються при близькому розташуванні (на відміну від `JournalTimeline`) —
  свідомо: кількість сесій на книгу природно обмежена (типово одиниці-десятки, не сотні записів
  щоденника), і кожна сесія — самостійна одиниця сенсу, а не довільний запис, яких може
  назбиратись багато в одному місці книги.
- Немає окремого редагування "Як читалося?" з цього екрана — значення й далі проставляється там,
  де завжди (`SessionReflectionPanel`, `app/session/[sessionId].tsx`, одразу після завершення
  сесії); ця шкала лише читає вже збережене.
- Шкала не враховує rereading окремо (черговий прохід рахує ті самі сесії, що й перший) — той
  самий клас компромісу, що вже задокументовано для інших V1.6 фіч при перечитуванні
  (`docs/BOOK_CAPSULES.md` §Архітектура).

## Архітектура (коротко)

- `src/lib/readingExperienceTimeline.ts` — чиста доменна функція
  `computeReadingExperienceTimeline` (позиціонування, поріг "замало даних") + константа
  `MIN_SESSIONS_FOR_READING_EXPERIENCE_TIMELINE`, покрита `readingExperienceTimeline.test.ts`.
- `src/components/memory/ReadingExperienceTimeline.tsx` — рендер шкали + тап→підпис.
- `app/memory/[workId].tsx` — підключення секції (`sessions`/`pageCount`, обидва вже
  завантажені цим екраном раніше).
