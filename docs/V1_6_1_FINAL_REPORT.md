# FINAL REPORT — POLYTSIA V1.6.1 «Foundation, Reading Runs, UX Consolidation & Calendar Evolution» (2026-09-13)

Підсумковий звіт після завершення всіх 28 фаз milestone'у POLYTSIA V1.6.1. Джерело фактів —
`CHANGELOG.md` (по кожній фазі), `docs/DATABASE.md`, `docs/READING_RUN.md`,
`docs/SOFT_DELETE_READINESS.md`, `docs/PRODUCT_CONSOLIDATION.md` (новий, той самий strand
документований у цьому звіті ще раз, коротко), реальні прогони CI (GitHub Actions) і статичний
аналіз репозиторію, виконаний цією сесією.

**Примітка про структуру цього звіту.** Точну структуру розділів, яку оригінальне ТЗ вимагало
для фінального звіту V1.6.1, було втрачено під час події стиснення контексту (context
compaction) раніше в цій робочій сесії — сам текст вимоги не відновлюється. Це не було
здогадане чи мовчки замінене: питання поставлено власнику продукту напряму, і власник обрав
розширити вже перевірену структуру `docs/FINAL_REPORT.md` (V1.5, 15 розділів) додатковими
розділами під нові виміри V1.6.1, а не намагатись реконструювати втрачену структуру за
здогадкою. Це рішення само по собі варте фіксації тут, у тому ж дусі, що й решта house-конвенції
цього репозиторію — документувати ЧОМУ, не лише ЩО. Розділи 1-15 нижче зберігають ті самі назви
й порядок, що й `docs/FINAL_REPORT.md`, з вмістом під V1.6.1 (28 фаз замість 16); розділи 16-23
— додаткові виміри, яких не було в scope V1.5.

## 1. Що було реалізовано

**Фаза 1 — P0 fix: "Не дочитав" більше не лишає хибну дату завершення.** Перехід
`finished → did_not_finish` тепер завжди скидає `user_book.finished_at`; новий Data Doctor check
`dnf_with_finished_at` ловить успадковані записи з часу до фіксу.

**Фаза 2 — legacy `app/characters/*` маршрути підтверджено видалені.** Перевірено напряму на
пристрої: обидва файли фізично відсутні; виправлено один застарілий коментар, що досі посилався
на старий шлях.

**Фаза 3 — централізована spoiler-safe policy.** Закрито 6 реальних витоків спойлерів: Personal
Search, Global Journal, Activity History, On This Day (реальний баг — фільтр ігнорував
`spoilerSafeEnabled` книги), Book Memory/Journal Timeline, Recall/Capsule — усі раніше без
жодної перевірки на багатокнижних поверхнях, попри те що режим "без спойлерів" уже існував з
V1.6 Фази 11.

**Фаза 4 — ключ Google Books прибрано з клієнта.** Новий Supabase Edge Function
`google-books-proxy` (Deno, IP-based rate limiting, той самий механізм, що й `isbndb-proxy`),
клієнт зберігає анонімний fallback, коли проксі не задеплоєно (свідома архітектурна відмінність
від ISBNdb — провайдер безкоштовний і не вимикається). OWNER ACTION: деплой Edge Function не
виконано з цієї хмарної сесії.

**Фаза 5 — прямі тести на транзакційну серцевину `ReadingSessionRepository`.** 23 нових тести на
`start`/`pause`/`resume`/`finish`/`discard` — методи, названі найважливішою прогалиною покриття
у V1.6.1-аудиті, до цього не мали ЖОДНОГО прямого repository-тесту. Продуктовий код не
змінювався.

**Фази 6-12 — REREADING MODEL.** Нова сутність `ReadingRun` і повний ланцюжок прив'язки до неї
шести залежних сутностей (сесії/спогад/До-Після/капсула/DNF/рейтинг). Детально — §16 нижче.

**Фази 13-19, 28 — UX Consolidation strand.** П'ять фаз консолідації навігації/IA (Book Memory

**Фаза 18 — Progressive onboarding.** Три одноразові контекстні підказки (welcome/перша сесія/
перше завершення книги), `expo-secure-store`-backed, друга половина FTUE-відповіді аудиту поруч

**Фаза 20 — Offline UX.** `useIsOffline()` (`expo-network`, перевіряє й реальну досяжність

## 3. Які migrations створені

Схема має **27 файлів міграцій** у `src/data/db/migrations/` (`001_base_schema.ts` …
`027_soft_delete_readiness.ts`), `LATEST_SCHEMA_VERSION` обчислюється як версія останньої
міграції в масиві (`src/data/db/migrationRunner.ts`) — підтверджено читанням директорії й
константи цією сесією: **27 збігається з фактичним станом репозиторію.**

POLYTSIA V1.6.1 додав 9 нових (019-027) поверх 18, що існували на кінець V1.6:

- **`019_reading_run.ts`** (Фаза 6) — адитивна `CREATE TABLE reading_run` (`run_number`/
  `status`/`is_legacy_backfill`/`deleted_at`). Нуль зміни продуктової поведінки — жоден інший
  файл коду її ще не викликає.
- **`020_reading_run_backfill.ts`** (Фаза 6b) — адитивна колонка `reading_session.reading_run_id`
  + єдина в проєкті міграція з процедурною (не чистою декларативною SQL) backfill-логікою в
  TypeScript (`generateId()` на рядок, багаторівнева `status`/`finished_at` логіка).
- **`021_book_memory_run.ts`** (Фаза 8), **`022_pre_reading_reflection_run.ts`** (Фаза 9),
  **`024_dnf_reflection_run.ts`** (Фаза 11), **`025_rating_run.ts`** (Фаза 12) — усі чотири
  rebuild-з-backfill за тим самим ідіомом (`_new`+`DROP`+`RENAME`, SQLite не підтримує `ALTER
  TABLE` для зміни `UNIQUE`): обмеження міняється з `UNIQUE(user_book_id)` на
  `UNIQUE(reading_run_id)`, щоб кожне прочитання книги мало власний, а не спільний перезаписний
  запис.
- **`023_book_capsule_run.ts`** (Фаза 10) — інакше: `book_capsule` НІКОЛИ не мала
  `UNIQUE(user_book_id)`, тож проста адитивна `ALTER TABLE ADD COLUMN reading_run_id` без
  rebuild; backfill — інший алгоритм (кожна з можливих кількох legacy-капсул книги бекфілиться
  ОКРЕМО, найближчий "знизу" за часом run).
- **`026_hot_query_indexes.ts`** (Фаза 24) — 5 нових композитних індексів
  (`edition(isbn10)`/`user_book(status, updated_at)`/`note(user_book_id, created_at)`/
  `quote(user_book_id, created_at)`/`reading_session(user_book_id, started_at)`) + видалення 4
  надлишкових одноколонкових індексів, які нові композити повністю замінюють
  (leftmost-prefix rule).
- **`027_soft_delete_readiness.ts`** (Фаза 26) — адитивна колонка `deleted_at` на
  `book_capsule`/`book_memory`/`rating`, без rebuild, без backfill.

Усі 9 підтверджені: upgrade наявної БД, тест на порожній БД, тест на заповненій БД
(`migrationRunner.test.ts`, по кожній окремо), і — з Фази 27 — ще й два наскрізні сценарії, що
проганяють цілий ланцюжок ЗА ОДИН стрибок (§22 нижче). `docs/DATABASE.md` оновлено по кожній.

## 4. Security changes

- **Фаза 4** — 🟡 знахідка `docs/SECURITY.md`/`V1_6_FULL_AUDIT_REPORT.md` (розділ 26/32):
  опційний `EXPO_PUBLIC_GOOGLE_BOOKS_API_KEY` компілювався в клієнтський бандл. Закрито тим
  самим шлюз-патерном, що й ISBNdb (V1.5 Фаза 1.1) — з архітектурною відмінністю: Google Books
  безкоштовний і має робочий анонімний fallback, тож провайдер НЕ вимикається без проксі, лише
  втрачає підвищену квоту. **OWNER ACTION: деплой `google-books-proxy` не виконано з цієї
  сесії** (немає доступу до Supabase CLI/credentials з хмарного середовища).
- **Фаза 21** — Backup privacy UX: явне попередження перед поширенням повного нешифрованого
  JSON-бекапу (усі приватні нотатки/цитати/DNF-причини/pre-reading рефлексії) через системне
  "Поділитися". Шифрування свідомо поза межами цього milestone'у (пряма вимога ТЗ Фази 21) —
  лише обізнане підтвердження перед фактичним поширенням.
- **Фаза 25** — `npm audit --audit-level=high` тепер реально запускається в CI (advisory,
  `continue-on-error: true`, той самий підхід, що й `expo-doctor`) — це закриває єдиний
  відкритий пункт §4 звіту V1.5 ("не перевірено в жодній хмарній сесії"). Точний список CVE
  для поточного lock-файлу з'явиться в логах реального прогону CI, не в цьому звіті (ця сесія
  так само без мережевого доступу до npm-реєстру — див. §12).
- Обидві P0-знахідки безпеки з V1.5 (ISBNdb-ключ, `book-covers` анонімний запис) лишаються
  закритими й не торкались цим milestone'ом; IP-based rate limiting — той самий, задокументований
  раніше pre-Auth компроміс.

синхронізація йде вибірково (лише файли, які ця сесія свідомо редагує й переносить через

висновку розділу: **813 — підтверджене реальним прогоном число**, а 753 — артефакт неповного
хмарного дзеркала, не сигнал про реальну відсутність тестів. Власнику продукту нема потреби

## 13. Residual risks

- **Хмарне дзеркало репозиторію цієї сесії відстає від реального стану на частину файлів,
  не торкнутих напряму** (§6) — статичний grep у дзеркалі дав 753 точки виклику `it`/`test`
  проти реальних 813 (підтверджених живим прогоном на машині власника продукту). Саме число
  813 — не під сумнівом; під сумнівом лише повнота хмарного дзеркала як джерела для БУДЬ-ЯКОГО
  майбутнього статичного аналізу цією сесією (наприклад, якщо майбутня фаза захоче порахувати
  щось інше статичним grep по дзеркалу — варто пам'ятати про цю розбіжність).
- **`ReadingRun`/REREADING MODEL — найновіша й найскладніша частина схеми** (9 нових міграцій,
  6 rebuild-з-backfill): попри вичерпне юніт/інтеграційне покриття кожної окремої міграції й,
  з Фази 27, два наскрізні сценарії "весь ланцюжок разом", жодна з цих міграцій ще не пройшла
  реальний device-рівень restore зі старого, справжнього бекапу користувача (лише синтетичні
  фікстури тестів) — той самий клас ризику, що вже фіксувала Фаза 27 сама про себе.
- **`ReadingRunRepository.discard()` існує, але ніде не викликається з UI** (з Фази 6) —
  користувач не має способу "скасувати" помилково створений reading run; не аномалія (жоден
  Data Doctor check не фіксує це як помилку — це forward-looking стан), але функціональна
  прогалина, якщо колись знадобиться "видалити помилковий запис перечитування".
- **IP-based rate limiting** на всіх трьох Edge Functions (isbndb-proxy/cover-upload/тепер і
  google-books-proxy) лишається тим самим pre-Auth компромісом, задокументованим ще в V1.5.
- **`google-books-proxy` не задеплоєно** — доки OWNER ACTION §12 п.1 не виконано, Google Books
  API-ключ (коли є) і далі не має проксі-захисту (хоч анонімний fallback і безпечний сам по
  собі).
- **Документація схильна застарівати швидше за код** — той самий структурний ризик, що й V1.5
  §13, підтверджений цим-таки milestone'ом: Фаза 23 сама виправляла фактичну помилку в
  CHANGELOG-записі Фази 19 V1.6 (5-денна затримка між реальною появою фічі й хибним
  твердженням про її відсутність).
- **Жодного реального прогону на фізичному пристрої/симуляторі** за весь V1.6.1 з хмарної сесії
  (§11) — той самий залишковий ризик, що й V1.5.

## 16. REREADING MODEL — ланцюжок міграцій `reading_run` (Фази 6-12)

**Проблема, яку вирішує.** До Фази 6 `user_book.status = 'rereading'` був лише мутабельним
прапорцем без жодного запису історії — `V1_6_FULL_AUDIT_REPORT.md` (розділ 23) назвав це
найбільшою структурною прогалиною архітектури V1.6: Wrapped/статистика недораховували
перечитувані книги, Book Memory й Before/After втрачали дані попереднього прочитання при
`upsert` (другий `upsert` безповоротно перезаписував перший), Capsule свідомо не пропонувалась
для перечитування взагалі.

**Ланцюжок фаз (кожна — окремий, самостійно протестований крок):**

1. **Фаза 6** (`019_reading_run.ts`) — сама сутність `ReadingRun`, нуль зміни продуктової
   поведінки, жоден інший файл коду її ще не викликає.
2. **Фаза 6b** (`020_reading_run_backfill.ts`) — `reading_session.reading_run_id` + legacy
   backfill: для кожної наявної книги щонайбільше ОДИН `reading_run` (`is_legacy_backfill = 1`)
   best-effort з наявних `started_at`/`finished_at`/сесій/статусу, без вигадування кількох
   старих перечитувань (пряма вимога ТЗ) — задокументована втрата інформації для книг зі
   статусом `rereading` до цієї фази.
3. **Фаза 7** — run-aware sessions: `UserBookRepository.updateStatus` тепер прив'язує реальний
   старт/завершення run до переходу статусу; нові сесії більше не мають `reading_run_id = NULL`
   за замовчуванням. Жодної нової міграції.
4. **Фази 8-11** (`021`/`022`/`024`) — Book Memory, Before/After, DNF по черзі прив'язані до
   `reading_run_id` через rebuild-з-backfill: кожне прочитання отримує ВЛАСНИЙ запис замість
   спільного, перезаписного.
5. **Фаза 10** (`023`) — Capsule/Recall, інша модель (не "найновіший = поточний", капсула
   фіксує своє прочитання назавжди) і інший вид міграції (адитивна, не rebuild).
6. **Фаза 12** (`025`) — рейтинг, восьма й остання частина: архітектурна прогалина, не виявлена
   жодною з попередніх шести фаз. Плюс явний CTA "Перечитати" на Book Details і два нові
   UI-екрани — "Історія прочитань" (accordion) і "Як змінилася книга для тебе" (порівняння ≥2
   завершених прочитань), що зводять докупи все, зроблене Фазами 6-11.

**Стратегія backfill (спільна для 021-025):** кожна легасі-запис шукає СВІЙ найближчий за часом
відповідний `reading_run` (не просто "найновіший run книги" — це помилково зчепило б кілька
старих записів різних прочитань з одним run), із задокументованим порядком фолбеку для кожної
таблиці окремо (наприклад: DNF-знімок кандидатує лише `did_not_finish`-run, ніколи `finished`;
рейтинг — і `finished`, і `did_not_finish`). Повна таблиця правил — `docs/READING_RUN.md`.

Детальний, по-фазовий розбір архітектурних рішень — `docs/READING_RUN.md`. Стислий підсумок
самого ланцюжка міграцій — §3 вище.
