# FINAL REPORT — POLYTSIA V1.5 «PERSONAL READING OS» (2026-09-10)

Підсумковий звіт після завершення всіх 16 фаз milestone'у POLYTSIA V1.5, за структурою,
вимогою самого ТЗ. Джерело фактів — `CHANGELOG.md` (по кожній фазі), `docs/DATABASE.md`,
`docs/SECURITY.md`, `docs/V2_READINESS.md`, реальні прогони CI (GitHub Actions) і реальні
прогони `npm run typecheck`/`npm test`/`npx eslint` на машині власника продукту.

## 1. Що було реалізовано

**Фаза 0-1 (Security P0, зроблено ще до формального старту 16 фаз, але в межах milestone'у):**
повний аудит репозиторію, дві реальні знахідки безпеки (розділ 4 нижче).

**Фаза 1.1 — ISBNdb-ключ прибрано з клієнта.** Платний ключ ISBNdb більше не компілюється в
мобільний білд — увесь виклик іде через новий Supabase Edge Function-проксі
(`isbndb-proxy`) з IP-based rate limiting, валідацією вводу й нормалізованими помилками.

**Фаза 1.2 — `book-covers` більше не приймає анонімний прямий запис.** Новий Edge Function
`cover-upload`: перевірка реального типу файлу за magic bytes, ліміт розміру, шлях об'єкта
генерує сервер (`crypto.randomUUID()`) — усуває і зловживання квотою, і path traversal.

**Фаза 2 — реальний CI.** Уперше в історії репозиторію створено git-репозиторій і
`.github/workflows/ci.yml` (`npm ci` → `tsc --noEmit` → `eslint --max-warnings=0` → `jest` →
`expo-doctor` advisory). Перший реальний прогін виявив і виправив 6 категорій давно існуючих,
але ніколи не перевірених автоматично проблем (розділ 2 нижче).

**Фаза 3 — repository-інтеграційні тести.** `expo-sqlite` не конструюється в headless Node
CI-раннері — перейшли на `better-sqlite3` як тестовий рушій (той самий SQL-діалект, продакшн-код
репозиторіїв не змінено жодним рядком). Це відкрило шлях до реальних repository-тестів, яких
до цієї фази не було ЖОДНОГО.

**Фаза 4 (+ продовження) — Backup Reliability.** Автоматизований round-trip тест резервної копії
на всіх 31 таблицях; знайдено й підтверджено критичну властивість (FK-safe порядок видалення
під час restore, transactional rollback) — уперше перевірено проти реального SQLite з увімкненим
FK-контролем. Окремо — фікс нестабільного `bookStats.test.ts` на Windows (`cross-env TZ=UTC`).

**Фаза 5 — Data Integrity Doctor («Перевірка даних»).** Новий екран, ручний запуск, 6 категорій
перевірок (книги/сесії/прогрес/щоденник/полиці/серії), без жодного destructive auto-repair.

**Фаза 6 — Personal Search («Особисте» проти «Каталог»).** Екран пошуку розділено на явні
режими: офлайн-пошук по власних даних (5 доменів) окремо від зовнішнього пошуку для додавання
книги (без змін).

**Фаза 7 — Journal Search.** «Мій щоденник» отримав повний пошук/фільтри (текст/книга/тип/
реакція/обране/дата). FTS5 свідомо відхилено на користь `LIKE` — задокументований аналіз
масштабованості.

**Фаза 8 — Reading Continuity.** Картка "Зараз читаєш" на Home тепер показує останній час/
тривалість сесії й прев'ю останньої думки, усе — опціонально, з graceful degradation.

**Фаза 9 — Session Reflection.** "Як читалося?" — необов'язкове поле з 5 фіксованих значень
після завершення сесії, окреме від наявної реакції-на-запис.

**Фаза 10 — Journal Memory Timeline.** Візуальна шкала 0-100% книги з маркерами записів
щоденника на Book Memory screen, з кластеризацією й preview по тапу.

**Фаза 11 — «Повернутися пізніше».** Новий прапорець на нотатках/цитатах, UI у трьох місцях,
фільтр у щоденнику, карти на екранах завершення книги й спогаду.

**Фаза 12 — «Моя історія» (Reading Activity History).** Новий unified read-only timeline-екран,
один SQL `UNION ALL` по 8 наявних джерелах, без нової таблиці.

**Фаза 13 — Backup Health UX.** Картка стану резервного копіювання (версія схеми, підрахунки,
час останнього експорту) + можливість перевірити файл бекапу без реального відновлення.

**Фаза 14 — Cleanup.** Виправлено технічний борг readiness-звіту: одна хибна знахідка
(`useJournalGlobalCount` насправді підключений), один застарілий route map (переписано), одне
питання про робочий файл (вирішено відсутністю файлу).

**Фаза 15 — Performance Review.** Знайдено й виправлено один підтверджений bottleneck
(N+1/full-scan у `ReadingGoalRepository.getProgress`); решта досліджених сценаріїв —
підтверджено коректними без змін.

**Фаза 16 — Design Polish.** Аудит усіх нових/змінених екранів проти чек-листа (тема, dynamic
text, малі пристрої, довгі українські рядки, empty/loading/offline/error states); один
підтверджений і виправлений фікс (порожній стан «Моя історія» без next action).

## 4. Security changes

Обидві P0-знахідки аудиту безпеки (`docs/SECURITY.md`) — **закриті, задеплоєні й перевірені
власником продукту реальними викликами** (2026-09-10):

- 🔴→⚪ Платний ключ ISBNdb прибрано з клієнта, `isbndb-proxy` Edge Function, rate limiting
  (20/60с burst + 300/добу на IP), `verify_jwt` лишається увімкненим.
- 🟡→⚪ `book-covers` більше не приймає прямий анонімний запис, `cover-upload` Edge Function,
  сервер сам генерує шлях об'єкта (усуває path traversal), rate limiting (10/60с + 100/добу).

Залишковий, свідомо задокументований ризик обох: IP-based rate limiting — найкращий доступний
pre-Auth варіант, не гарантія (спільний NAT/VPN). Повне закриття цього ризику вимагає реального
Supabase Auth (V2, свідомо поза межами цього milestone'у).

**Не перевірено в жодній хмарній сесії:** `npm audit` (немає доступу до npm-реєстру в цьому
середовищі) — єдиний відкритий пункт аудиту безпеки, OWNER ACTION (розділ 12).

## 8. Backup round-trip result

✅ **PASS.** Автоматизований тест (Фаза 4) — `create representative DB → export → fresh DB →
restore → compare` на всіх 31 таблицях, ще й окремо: FK-safe порядок видалення під реальним
`PRAGMA foreign_keys = ON`, transactional rollback при навмисно зламаному FK,
`MIN_COMPATIBLE_BACKUP_SCHEMA_VERSION ≤ LATEST_SCHEMA_VERSION` invariant. Обидві нові міграції
V1.5 (010, 011) пройшли той самий round-trip без жодної зміни тесту. `BackupRepository.test.ts`
— у зеленому прогоні Фази 16 без жодної регресії.

## 9. Performance findings

Фаза 15, сценарії ТЗ (1000 книг / 5000 сесій / 10000 записів щоденника):

- **Підтверджено й виправлено:** `ReadingGoalRepository.getProgress` (minutes/pages/
  reading_days) — був N+1/full-scan (`listAllCompleted().filter()` окремо на кожну ціль),
  замінено на SQL-звужений `listStartedBetween(periodStart, periodEnd)`.
- **Перевірено й підтверджено коректним без змін:** `ActivityHistoryRepository` (`UNION ALL`),
  Series/Edition (малі N), `UserBookRepository` (unbounded SELECT виправдано розміром
  бібліотеки одного користувача), journal feed/personal search (keyset-пагінація), журнал-фід
  `ItemSeparatorComponent` (косметика, не performance), `BackupRepository.exportAll`
  (навмисно `SELECT *` — генеричність backup-формату важливіша за швидкість, і backup —
  нечаста, не hot-path операція).
- **FTS5 (повнотекстовий пошук)** — проаналізовано двічі (Фази 6 і 7), свідомо відхилено:
  `LIKE`-скан лишається <50мс навіть на заявлених обсягах; FTS5 вимагав би нової віртуальної
  таблиці/тригерів і непідтвердженої сумісності з `expo-sqlite` на iOS/Android. Ревізувати,
  якщо власник продукту повідомить про реальне гальмування.

## 13. Residual risks

- **17 з 29 репозиторіїв без repository-тестів** (розділ 7) — найбільший технічний ризик:
  регресія в, наприклад, `UserBookRepository` (основний CRUD бібліотеки) чи
  `ReadingProgressRepository` не буде спіймана автоматично, лише ручним тестуванням.
- **IP-based rate limiting** на обох Edge Functions — свідомо задокументований pre-Auth
  компроміс, не справжній захист від рішучого зловмисника з VPN/ротацією IP.
- **`npm audit` невідомий** для поточного стану залежностей.
- **Жодного реального прогону на фізичному пристрої/симуляторі** за весь V1.5 з хмарної сесії
  — весь UI/UX (включно з Фазою 16 design polish) верифіковано читанням коду й
  typecheck/lint/test, не візуально.
- **Документація схильна застарівати швидше за код** — за цей milestone виявлено щонайменше
  4 випадки застарілих/самосуперечливих ділянок документації (`ARCHITECTURE.md` route map,
  `V2_READINESS.md` розділ 8, і, щойно при фінальному огляді, `SECURITY.md`/`V2_READINESS.md`
  розділ 7) — рекомендація: періодичний, а не лише реактивний, аудит документації.
- **Віддалений місток до файлів власника продукту іноді мовчки не записує файл** (розділ 2) —
  мітигується обов'язковою повторною перевіркою після кожного запису, але сам механізм
  лишається джерелом ризику для будь-якої майбутньої сесії, що працює тим самим способом.

## 14. Що НЕ було реалізовано навмисно

Точно за розділом ТЗ "DO NOT IMPLEMENT YET" — жодного з них не торкались: Supabase Auth,
акаунти, nickname, друзі, соціальна стрічка, книжкові клуби, дует читання, коментарі,
підписки, оплата, AI-асистент, LLM-підсумки, акаунти видавців, публічні профілі, прямі
повідомлення, складний recommendation engine. `docs/V2_READINESS.md` розділ 10 документує, що
саме вже архітектурно готове для кожного з них, коли настане час.

Окремо, свідомо відкладено в межах самого V1.5 (не "ніколи", а "не зараз"):

- **FTS5 повнотекстовий пошук** — LIKE-скан достатній на заявлених обсягах (розділ 9).
- **Destructive auto-repair у Data Doctor** — пряма вимога ТЗ Фази 5, лише знаходження й
  навігація.
- **Довільний діапазон дат** у фільтрах "Мій щоденник" — пресети покривають реальні сценарії
  (Фаза 7).
- **Push-сповіщення для "Повернутися пізніше"** — пряма вимога ТЗ Фази 11.

## 15. Рекомендація: чи готова «Полиця» до V2 Auth

**Так, архітектурно готова — з трьома застереженнями.** Repository-шар уже відокремлений від
UI (`user_id` буде адитивною міграцією, не переписуванням); обидва P0-ризики безпеки закриті й
перевірені; CI/тестовий запобіжник тепер реальний і зелений на всіх 16 фазах; backup/restore
підтверджено round-trip-безпечним, включно з обома новими міграціями.

Перед тим, як відкривати V2 (Auth, більше користувачів — а отже й більший масштаб наслідків
будь-якої недогляну), варто закрити:

1. **`npm audit`** на реальній машині — знати точний список CVE перед тим, як розширювати
   аудиторію.
2. **Реальний прохід по manual device checklist** (розділ 11) — це перший milestone, де UI
   дійсно вручну не перевірявся на пристрої з боку асистента; варто підтвердити, що жоден
   із 16-и фаз не привніс візуальну регресію, яку не ловить `jest`/`tsc`.
3. **Свідомо прийняти (чи заздалегідь спланувати міграцію від) IP-based rate limiting** —
   як тимчасовий, а не постійний стан: щойно з'явиться Auth, rate limit варто перевести на
   per-user, не лишати на IP навіть після того, як з'явиться "справжня" ідентифікація.

З цими трьома пунктами закритими — нічого, знайденого за весь V1.5, не вимагає відкату чи
переробки перед V2. Рекомендація: переходити до Auth як наступного milestone'у.

---

*Головна мета milestone'у (за самим ТЗ): «Полиця» після V1.5 — не просто застосунок з великою
кількістю функцій, а надійна персональна читацька система, якій користувач може довірити роки
своєї читацької історії. За результатами всіх 16 фаз (безпека закрита й перевірена, реальний CI/
тести замість ручної перевірки, backup підтверджено round-trip-безпечним, продуктивність
перевірена на заявлених обсягах, дизайн узгоджено перевірено без регресій) — ця мета досягнута
в межах того, що можна перевірити без реального пристрою (розділ 11 вище — останній залишений
крок).*
