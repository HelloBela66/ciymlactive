# SPOILER_SAFE.md — режим «без спойлерів» (Фаза 11)

POLYTSIA V1.6, Фаза 11 (SPOILER-SAFE MODE). Цей документ фіксує точну поведінку фічі й
архітектурне рішення, яке інакше довелось би пояснювати заново при кожній фазі (той самий підхід,
що й `docs/PERSONAL_LORE.md`/`docs/BOOK_CAPSULES.md`/`docs/RECALL.md`).

## Мета

ТЗ Фази 11 називає це "important product principle": для записів щоденника й елементів лору, де
відома сторінка/прогрес, застосунок повинен приховувати те, що трапилось ПОПЕРЕДУ поточного
прогресу читання — щоб користувач, гортаючи нотатки/світ книги під час активного читання, не
наштовхнувся на власний же запис, що виказує розвиток сюжету, якого він ще не дочитав.

Ключове обмеження з ТЗ: **"Не видаляй записи. Тільки hide/filter."** Це не окрема функція
видалення чи архівування — режим лише змінює, що видно на екрані ПРЯМО ЗАРАЗ; вимкнення прапорця
миттєво повертає всі записи на місце.

## Рівень: `user_book`, не `work`

Прапорець `spoiler_safe_enabled` — book-level setting (ТЗ: "Book-level setting"), колонка на
`user_book` (`016_spoiler_safe.ts`), не на `work`. Причина та сама, що й для `current_page`:
поняття "наскільки далеко я зараз" належить КОНКРЕТНОМУ читанню користувача, а не твору взагалі
— той самий рівень, на якому вже живе сам прогрес, з яким режим порівнює позицію записів.

```sql
ALTER TABLE user_book ADD COLUMN spoiler_safe_enabled INTEGER NOT NULL DEFAULT 1;
```

`DEFAULT 1`, а не nullable-полe чи `DEFAULT 0` — ТЗ прямо каже "Default: ON для active books".
Існуючі книги (додані до цієї міграції) отримують `1` заднім числом без наслідків: сам прапорець
нічого не приховує без активного читання (`isSpoilerSafeActive` нижче), тож заднім числом
увімкнене налаштування не змінює поведінку жодної вже прочитаної чи ще не розпочатої книги.

## Коли режим реально активний

```ts
function isSpoilerSafeActive(status: UserBookStatus, spoilerSafeEnabled: boolean): boolean {
  return spoilerSafeEnabled && (status === 'reading' || status === 'rereading');
}
```

Прапорець сам по собі — лише налаштування; приховування вмикається, тільки коли книга РЕАЛЬНО
читається (`reading`) чи перечитується (`rereading`). Для `finished`/`did_not_finish`/`paused`/
`want_to_read` приховувати нічого не потрібно: прочитана книга не має "попереду" в сенсі спойлера
(усе вже прочитано), ще не розпочата — записів попереду фізично ще нема, а "на паузі" — той самий
випадок, що й "читаю", але ТЗ явно обмежує лише `reading`/`rereading`, тож `paused` свідомо
лишений поза межею активного режиму (як і `did_not_finish`).

## Порівняння позиції

Кожен запис (нотатка/цитата/елемент лору) може мати `page` (пріоритет) і/або `progressPercent`/
`firstSeenProgress` (фолбек). Порівняння — з `user_book.current_page` (і `pageCount` видання для
переведення в проценти):

1. Якщо і в запису, і в поточного прогресу є сторінка — порівнюються сторінки напряму.
2. Інакше, якщо в обох є відсоток прогресу — порівнюються відсотки.
3. Якщо жодної зі сторін порівняти неможливо — запис **лишається видимим** (консервативний
   дефолт: хибне приховування гірше за хибний показ, а довести "попереду" неможливо без жодної
   позиції з будь-якого боку).

Уся логіка — чисті функції в `src/lib/spoilerSafe.ts` (той самий house-патерн, що й
`bookCapsule.ts`/`staleReading.ts`: жодного `new Date()`/SQL/React усередині, `now`/поточний
прогрес — завжди явний параметр): `isSpoilerSafeActive`, `filterSpoilerSafeJournalEntries`,
`filterSpoilerSafeLoreEntities`.

## Перечитування

ТЗ: "Особливо важливо: під час rereading можна створити new reading run. Spoiler-safe mode може
враховувати поточний reread progress. Не руйнуй existing rereading model." — `current_page` під
час `rereading` уже й так відображає прогрес ПОТОЧНОГО прочитання (той самий інваріант, що
використовує `FinishPredictionSection`/`StaleReadingSection`), тож `isSpoilerSafeActive`/фільтри
не потребують жодної окремої гілки для перечитування — вони просто читають те саме поле.

## Де застосовується (і де свідомо ні)

Фільтр застосований на клієнті, над уже завантаженим масивом (той самий підхід, що й
`revisitLaterOnly`/`favoriteOnly` — жодного SQL-рівня виключення чи видалення) у трьох місцях:

- `app/work/[workId].tsx`, `JournalSection` — список нотаток/цитат книги на Book Details.
- `app/lore/[workId].tsx` та компактна картка `LoreSection` (і на Book Details, і на Book
  Memory) — елементи світу книги.
- `app/recap/[workId].tsx` — екран прямо названий у ТЗ як такий, що "гарантує spoiler-safe
  experience"; "Останні записи"/"Улюблений момент" рахуються з уже відфільтрованого списку.

Свідомо ПОЗА межами цього проходу (задокументоване обмеження, не недогляд):

- `JournalTimeline` (`app/memory/[workId].tsx`) — самостійна візуалізація ВСІХ записів
  щоденника як шкали 0–100% книги; сам сенс шкали — показати розподіл записів по всій книзі, а
  не окремі їхні тексти, тож спойлер-ризик тут інший і значно нижчий, ніж читати текст запису
  напряму.
- Пікери записів на екранах, доступних лише для вже завершених книг (капсула, спогад-картка,
  recall) — там `status` уже `finished`/`rereading`-після-фінішу, спойлерів по визначенню немає.
- Глобальна стрічка "Мій щоденник" (`app/journal/index.tsx`) — крос-книжковий фід, поза межами
  book-level налаштування цієї фази.

## UI

Перемикач "Приховувати майбутні записи" — картка в `LibrarySection` (`app/work/[workId].tsx`),
видима лише коли `status` — `reading`/`rereading` (той самий гейт, що й сама активація режиму).
Той самий `Pressable` + `Card` + іконка-перемикач патерн, що й позначка "є у мене фізично" —
жодного окремого `Switch`-компонента в кодовій базі немає.

Коли частину записів приховано, а не просто список порожній, `app/lore/[workId].tsx` і
`JournalSection` показують коротке пояснення ("Ще N приховано режимом «без спойлерів».") замість
тихого порожнього стану — це свідоме налаштування користувача, а не брак даних, тож "quiet
degradation" тут недоречний: людина має розуміти, чому список коротший, ніж вона очікує.

## Приватність

Жодних мережевих викликів, жодного AI/LLM — фільтрація суто клієнтська, над даними, які
користувач і так уже зберіг локально (той самий принцип, що й решта memory-фіч,
`docs/BOOK_CAPSULES.md` §Приватність). "SPOILER SAFETY" у `docs/V1_6_SPEC.md` (загальний розділ)
уточнює: застосунок ніколи не підвантажує сюжет/опис персонажів ззовні для активної книги — цей
режим стосується виключно того, що вже записав сам користувач.
