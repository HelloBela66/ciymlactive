# LOCAL_FIRST.md

## Принцип

SQLite — не кеш перед сервером, а основне сховище. Жоден екран core loop (Home, timer,
progress, notes) не має мережевого запиту на критичному шляху.

**Оновлено, Milestone 8.2**: Supabase тепер підключений — але лише для одного вузького,
некритичного випадку: спільний кеш метаданих книг на екранах пошуку/сканування ISBN
(`docs/SHARED_CATALOG.md`), щоб не витрачати платний ISBNdb-запит повторно на книгу, яку вже
підтвердив інший користувач. Це не суперечить принципу вище — пошук і так уже мережевий
(Milestone 7, зовнішні провайдери книг), а не core loop; без налаштованого Supabase-проєкту
ці екрани просто пропускають цей крок і працюють так само, як до Milestone 8.2. Жодна інша
частина застосунку (бібліотека, сесії читання, нотатки, статистика тощо) і далі не робить
жодного мережевого запиту на критичному шляху, і `@supabase/supabase-js` SDK свідомо НЕ
використовується (простий `fetch` до PostgREST RPC, `src/data/remote/sharedCatalogClient.ts`)
— не додає нової залежності.

## Repository pattern як межа майбутньої синхронізації

Кожен агрегат має один repository-файл (`src/data/repositories/*.ts`) з методами
`create/update/softDelete/getById/list/query`. Будь-яка мутація проходить через ці методи —
ніколи прямий `db.runAsync` з екрана. Це дає одну точку, куди пізніше додається:

```ts
async function markDirty(table: string, id: string) {
  // no-op у V1; пізніше — INSERT/UPDATE у sync_queue або UPDATE dirty=1
}
```

Коли з'явиться sync (не в цьому релізі), додаються міграцією стовпці `server_id`,
`dirty`, `synced_at` — без зміни сигнатур репозиторіїв і без зміни викликів у features.

## Що НЕ робимо зараз (і чому це свідомий вибір, а не недогляд)

- Немає realtime підписок, немає conflict-resolution engine, немає background sync job.
  Реалізація цього без другого реального пристрою для тестування — гарантований latent bug
  у read-моделі, якою користувач користується щодня; ризик не виправдовує вигоду в V1
  (один користувач, один пристрій).
- Немає `user_id` в жодній таблиці V1 — увесь застосунок неявно "один локальний користувач".
  Додавання auth пізніше — це міграція, що проставляє `user_id` існуючим рядкам значенням
  локального "default user" при першому вході, а не переписування схеми.

## Offline-індикатор

Мережа потрібна лише для (M7) пошуку метаданих. `NetInfo`-подібний стан (через
`expo-network`, за потреби) показує делікатний inline-banner лише на екрані пошуку/сканера,
ніколи глобальний блокуючий overlay — offline не повинен відчуватись як "застосунок
зламаний" (п.40).
