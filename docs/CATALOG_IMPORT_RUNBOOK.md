# Каталог: додавання нових книг — runbook

Покрокова процедура доливання нових книг у `curated_book`. Повний опис архітектури пайплайну —
`docs/OWN_CATALOG_IMPORT.md`; тут лише те, що робиться руками, у якому порядку і що має
статись на кожному кроці.

Стан на 16.09.2026: **30 726 книг**, 30 701 обкладинка під `curated/`, 25 книг без обкладинки
(22 у форматі GIF, 3 без посилання взагалі), 1 сторонній об'єкт у корені bucket.

---

## Два місця, де виконуються команди

* **PowerShell, `C:\polytsya-m11`** — скрипти імпорту й прибирання.
* **PowerShell, `C:\bookye-parser`** — парсер дампів.
* **Браузер, Supabase → SQL Editor** — перевірки. Панель результатів показує вивід ЛИШЕ
  останнього оператора й обмежує його сотнею рядків, тож складні запити виконуй по одному, а
  «Download CSV» не використовуй як вивантаження даних — він віддає тільки те, що на екрані.

## Крок 0. Переконатись, що нічого не загубиться

жанрів із `SEED_GENRES` і `purposes` там немає: усе це робить парсер.

```powershell
cd C:\bookye-parser
```

Якщо дамп обірваний (браузер закрили посеред вивантаження) — спершу ремонт:

```powershell

```

## Крок 1. Відсіяти те, що вже є в каталозі

Гнати через парсер увесь дамп безглуздо: більшість книг у каталозі вже є. З дампів 12 і 16
вересня з 5031 запису новими виявились 1154 — решта 3868 уже лежали в базі.

Зіставлення робиться за ISBN. **Книгу без ISBN так відсіяти неможливо** — це реальне обмеження,
через нього 11 дублікатів дійшли аж до dry run і були впіймані вже за збігом слага.

Готового скрипта для цього кроку немає: зараз він робиться разово. Якщо доливання стане
регулярним — його варто оформити окремим інструментом.

## Крок 2. Парсер

```powershell
.\run.bat out\<новий-дамп>.jsonl out\books_new.csv --legacy-contract
```

`--legacy-contract` прибирає порожню колонку `ReccOmenDuiT` — імпорт її однаково ігнорує, але
без неї файл чистіший.

У підсумку дивись на розподіл: `READY` іде далі, `REVIEW` лягає в `out\curated-review.csv` і
потребує очей, `EXCLUDED` відкинуто. На дампах 12/16 вересня з 1154 книг `READY` було лише 497 —
більш ніж половина пішла в `REVIEW`. Це не втрата, але й не «залилось усе».

## Крок 3. Партії

```powershell
python prepare_for_import.py out\books_new.csv --out-dir out\import-new --batch 3000
```

Скрипт повторює перевірки `validate.js` і показує, що імпорт відкинув би, — до того, як ти
витратиш час на apply. Партії по 3000 рядків: одна партія ≈ 2 хвилини, і кожна має власний звіт
та власну точку перезапуску.

## Крок 4. Dry run

```powershell
cd C:\polytsya-m11
node scripts/sync-curated-books.js ..\bookye-parser\out\import-new\books-001.csv
```

Dry run нічого не пише і нічого не качає, але **звіряється з реальним каталогом** — тож його
числа збігаються з тим, що зробить apply.

На що дивитись:

| рядок звіту | що означає |
| --- | --- |
| `Створено (нові)` | стільки книг з'явиться |
| `Оновлено (існували)` | стільки наявних книг буде **перезаписано** даними з цього файлу |
| `ISBN_TAKEN_IN_CATALOG` | ця книга вже є під іншим слагом — рядок відсіяно ще до мережі |
| `Помилок` | рядки, які в базу не потраплять |

**Якщо `Оновлено` більше нуля, а ти хотів лише долити нове** — додай `--only-new`. Без нього
апсерт мовчки перезапише наявні книги: саме так 16.09.2026 1372 книги отримали описи зі
старішого набору, і довелось окремим прогоном повертати канонічні дані.

## Крок 5. Заливка

```powershell
node scripts/sync-curated-books.js ..\bookye-parser\out\import-new\books-001.csv --apply --only-new
```

Концурренси 6 (за замовчуванням) book-ye витримує: 30 тисяч обкладинок залились за 50 хвилин без
жодного 429 і жодного таймауту. Знижувати до `--concurrency=3` є сенс ЛИШЕ якщо у звіті
з'являться `COVER_HTTP_ERROR` або `COVER_DOWNLOAD_FAILED` — це ознаки троттлінгу. Відмови з
кодом `COVER_INVALID_IMAGE` до швидкості не мають стосунку.

**Прогін перервався?** Запусти ту саму команду знову. Уже залиті обкладинки будуть
перевикористані (`Обкладинок повторно`), а не завантажені вдруге: шлях детермінований
(`curated/{id}.{ext}`), тож повтор — це перезапис того самого файлу, а не новий.

### Коди у звіті, які нічого не ламають

* `POTENTIAL_SERIES_METADATA` — «Книга 2» у назві без окремих полів серії. Формат їх поки не
  підтримує; книга імпортується нормально.
* `COVER_INVALID_IMAGE` — джерело віддало GIF (або HTML замість картинки). Bucket приймає лише
  JPEG і PNG, тож книга лягає з `cover_url = null`. У всьому каталозі таких 22.
* `SUSPICIOUS_SHORT_DESCRIPTION`, `NO_GENRES` — книга імпортується, але без жанру не потрапить у
  «Що почитати завтра?»: там жанр обов'язковий.

### Коди, які варто прочитати

* `COVER_UPLOAD_FAILED` — відмова Storage. Одиничні випадки транзієнтні (за 30 тисяч обкладинок
  їх було 3) і лікуються повтором тієї самої команди. Якщо їх десятки — дивись деталі HTTP у
  повідомленні звіту.
* `DB_UPSERT_FAILED` — база відхилила рядок. Повідомлення містить справжню відповідь Supabase.
* `ISBN_TAKEN_IN_CATALOG` — не помилка пайплайну, а факт про дані: та сама книга вже є під
  іншим слагом.

## Крок 6. Перевірка

Supabase → SQL Editor, одним запитом:

```sql
select
  (select count(*) from curated_book)                                   as knyg,
  (select count(*) from curated_book where cover_url is null)           as bez_oblozhky,
  (select count(*) from storage.objects
     where bucket_id = 'book-covers' and name like 'curated/%')          as pid_curated;
```

`knyg` має вирости рівно на `Створено (нові)` зі звіту.

## Крок 7. Прибирання сховища (за потреби)

Пайплайн прибирає за собою сам: обкладинку відхиленого рядка видаляє той самий прогін, що її
завантажив. Окремий скрипт потрібен лише для історичного сміття.

```powershell
node scripts/cleanup-curated-covers.js --orphans
node scripts/cleanup-curated-covers.js --orphans --apply
```

Обидва режими за замовчуванням — dry run, повний перелік кандидатів пишеться на диск ДО
видалення, а після видалення кількість звіряється з очікуваною.

Другий режим, `--days=РРРР-ММ-ДД,...`, чистить КОРІНЬ bucket за датами створення. Він потрібен
лише для об'єктів, залитих до вересня 2026, коли імпорт ще клав файли в корінь під випадковими
іменами. Дозвільний список дат обов'язковий: без нього скрипт відмовляється працювати.

## Що зараз не автоматизовано

* **Відсів дублів за ISBN перед парсером** (крок 1) — робиться разово.
* **Книги без ISBN** неможливо зіставити з каталогом заздалегідь; вони ловляться лише збігом
  слага, тобто вже на dry run, і видно їх як `Оновлено (існували)`.
* **Дві схеми транслітерації в парсері.** `iakshcho` проти `yakshcho`, `iurkivky` проти
  `yurkivky` — один і той самий ISBN під двома слагами. Саме це дало 411 конфліктів 16.09.2026.
  Тепер вони відсіюються до мережі (`ISBN_TAKEN_IN_CATALOG`), але **причина лишається в
  парсері** і повторюватиметься на кожному імпорті, доки схему не звести до однієї.
* **Серії.** `series_name`/`series_position` формат не підтримує; ~3500 книг мають номер тому
  прямо в назві.
* **654 книги в `REVIEW`** з дампів 12/16 вересня чекають розбору в `out\curated-review.csv`.
