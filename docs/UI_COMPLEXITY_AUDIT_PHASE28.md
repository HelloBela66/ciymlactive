# UI_COMPLEXITY_AUDIT_PHASE28.md

POLYTSIA V1.6.1, Фаза 28 — фінальна фаза milestone "Foundation, Reading Runs, UX Consolidation &
Calendar Evolution". ТЗ (дослівно, з таск-трекера): "Після consolidation повторно перевірити, що
користувач розуміє де читати/записувати/згадувати/дивитись статистику/обирати наступну книгу.
Library — лише bug fixes, без нового redesign. Book Details — зменшити conceptual overload без
втрати features."

Це НЕ повний редизайн — повторний аудит ПІСЛЯ того, як Фази 13-19 (`MEMORY_HUB.md`,
`MY_READING.md`, `HOME_REFINEMENT.md`, `CALENDAR_2_0.md`, `NEXT_READ.md`) уже зробили основну
консолідацію навігації/рекомендацій. Мета — перевірити, чи п'ять базових намірів користувача
("де читати", "де записати", "де згадати", "де подивитись статистику", "де обрати наступну книгу")
досі зчитуються з кожного з шести екранів, і за потреби — точкові, адитивні виправлення.

## Метод

Прочитано всі consolidation-доки Фаз 13-19 і відповідні записи `CHANGELOG.md`, щоб не перезаявляти
вже виправлене; потім — сам код шести екранів (`app/(tabs)/index.tsx`, `app/(tabs)/library/
index.tsx`, `app/work/[workId].tsx`, `app/(tabs)/calendar.tsx`, `app/memory/index.tsx`,
`app/(tabs)/profile/index.tsx`) і прямі дочірні компоненти/хуки кожного.

## Результат по екранах

**Home, Calendar, Memory, Profile** — жодних знахідок. Усі чотири вже пройшли власну
консолідацію в Фазах 13-19 і читаються добре: п'ять намірів там, де вони застосовні до екрана,
чіткі; жодних дублюючих чи неоднозначних CTA не знайдено. Код цих екранів у цій фазі НЕ змінений.

**Library** — знайдено 2 реальні баги (не redesign, як і вимагало ТЗ):

1. `BookQuickActionsSheet`, шторка швидких дій довгим тапом — `ChipSelect` статусу всередині неї
   контрольований із снепшота `actionsForBook` (`app/(tabs)/library/index.tsx`), який не
   оновлювався після зміни статусу (мутація лише інвалідовує кеш списку книг, не сам цей
   локальний стейт) — вибраний чіп візуально "застрягав" на старому значенні. Перша версія фіксу
   (`useEffect`, що перепідв'язує снепшот на свіжий рядок зі списку книг) не пройшла
   `react-hooks/set-state-in-effect` цього проєкту — знайдено власним `eslint`-запуском
   користувача до коміту. Остаточний фікс — без окремого стейту й без ефекту взагалі: `actionsForBook`
   тепер похідне значення (`useMemo` за `id`), що рахується прямо в рендері зі свіжого `books`.
2. `ShelfRepository.listAll`/`search` — `bookCount` полиці рахував рядки `shelf_book`, а не живі
   книги: `UserBookRepository.remove` (м'яке видалення) ніколи не чистить `shelf_book`, тож
   прибрана з бібліотеки книга й далі рахувалась у лічильнику полиці. Виправлено другим `LEFT
   JOIN` на `user_book` з фільтром `deleted_at IS NULL`; заодно `useRemoveFromLibrary` тепер
   інвалідовує кеш полиць (раніше — ні), інакше SQL-фікс не був би видимий, доки не спливе
   власний `staleTime`. Регресійні тести — `ShelfRepository.test.ts` (новий файл).

**Book Details** (`app/work/[workId].tsx`) — єдиний екран з реальним "conceptual overload":
15 можливих секцій, з яких для активно читаної книги з рейтингом/щоденником/історією 10
рендеряться безумовно й одна за одною, і серед них три (`LibrarySection`/`StaleReadingSection`/
`LoreSection`) не мали ЖОДНОГО заголовка — виглядали як довільні картки без назви, а не
поіменовані частини екрана. `CollapsibleSection`'s власний doc-коментар уже прямо називає це
"свідомим, обмеженим трейд-офом" Фази 2 — ця фаза не переглядає ту стратегію, лише продовжує її:

- `LibrarySection` — додано заголовок "Бібліотека" (сам розділ і жоден контроль усередині не
  змінені).
- `StaleReadingSection` ("Давно не читав") — додано caption-підпис, той самий рівень, що вже мав
  `FinishPredictionSection` ("Орієнтовна дата завершення") поруч.
- "Історія прочитань" + "Історія читання" — були двома сусідніми незалежними
  `CollapsibleSection`, обидва вже згорнуті за замовчуванням, обидва про "погляд назад" на минулі
  прочитання. Об'єднано під один спільний toggle "Історія" із двома підзаголовками
  ("Прочитання"/"Сесії читання") всередині — користувачу більше не треба розгортати два окремих
  перемикачі. Жодна з двох секцій сама по собі не змінена, лише спільна обгортка.
- `LoreSection` ("Світ книги") — раніше завжди розгорнута незалежно від статусу книги, навіть
  коли лору ще нуль (тоді показувала лише "Світ цієї книги ще порожній." + кнопку — вага картки
  без інформації). Загорнуто в `CollapsibleSection`, той самий ідіом, що й історія/видання —
  функція (лічильник з урахуванням spoiler-safe, перехід на `/lore/[workId]`) не змінена.
- "Перечитати" CTA (REREADING MODEL, Фаза 12) — була ОКРЕМА картка (Card з іконкою+шевроном)
  поруч із чіпом статусу, що вже пропонує той самий перехід через опцію "Перечитую". Полегшено
  до підпису-посилання прямо під чіпом — той самий виклик `handleStatusChange('rereading')`, той
  самий текст пояснення, без ваги окремої картки. Це НЕ те саме, що видалення — вхідна точка й
  дія лишаються, лише менш візуально важкі.

### Свідомо НЕ зроблено (відхилення від початкового аудиту, задокументовано явно)

Початковий аудит також пропонував згрупувати `StaleReadingSection` і `FinishPredictionSection`
під одним спільним заголовком (обидва — сигнали "читання зараз"). Це НЕ зроблено: обидва
компоненти самі вирішують, показуватись їм чи ні (`if (...) return null` усередині, залежно від
статусу книги й наявності даних про темп/сесії) — спільний видимий заголовок над ними вимагав би
або підняти цю умову в батьківський компонент і продублювати її (ризик розбіжності при майбутній
зміні однієї з двох умов), або змінити сам контракт повернення компонентів. Ціну змінити
поведінку заради візуального групування визнано вищою за виграш — замість цього обидві картки
отримали власний caption-підпис (той самий візуальний рівень, що вже мав `FinishPredictionSection`),
що вирішує саму скаргу аудиту ("непоіменована картка серед інших") без ризику для гейтингу.

Ідея "Перечитати CTA → helperText-проп самого `ChipSelect`" також відхилена: `ChipSelect` —
спільний, багаторазово використовуваний компонент (формат видання тощо); додавання
book-details-специфічного пропу в нього заради одного викликання розширило б публічний API
спільного компонента заради локальної потреби. Замість цього — окремий, локальний `Pressable`
у самому `LibrarySection`, як і було.

Library — жодних layout/redesign змін, лише 2 баги вище, точно за межами ТЗ цієї фази.
