# SHARED_CATALOG.md — спільний каталог книг (Milestone 8.2)

## Навіщо

Пряме прохання користувача: не витрачати платний ISBNdb-запит повторно на ту саму книгу,
яку вже шукав чи додав собі інший користувач застосунку. Локальний SQLite на кожному
пристрої (`docs/LOCAL_FIRST.md`) принципово не може бути "спільним" — потрібне окреме,
справді спільне сховище. Це перший реальний випадок використання Supabase-заготовки, яка
існувала з Milestone 0 лише як плейсхолдер у `.env.example`/`app.config.ts`.

**Це не порушує local-first принцип.** Core loop (Home, таймер, прогрес, нотатки) як і
раніше повністю офлайн і не робить жодного мережевого запиту. Спільний каталог — лише
оптимізація ЕКРАНІВ ПОШУКУ/СКАНУВАННЯ ISBN (уже мережеві за своєю природою, Milestone 7):
без налаштованого Supabase вони просто продовжують працювати так само, як до цієї фічі.

## Що саме зберігається

Тільки метадані книг (назва, автори, ISBN, видавництво, обкладинка тощо) і анонімний
лічильник "скільки різних пристроїв додали цю книгу собі" (`catalog_book_device`, ключ —
випадковий UUID пристрою, `src/lib/deviceId.ts`, без жодного зв'язку з персональними даними
— в застосунку й так немає акаунтів). **Жодних нотаток, оцінок, прогресу читання чи іншого
особистого контенту користувача сюди не потрапляє** — лише те, що й так публічно доступне
через Google Books/ISBNdb.

## Як застосувати (одноразово, для власного Supabase-проєкту)

1. Зареєструйся/увійди на [supabase.com](https://supabase.com) → **New project** (безкоштовний
   план достатній: до 500 МБ бази й 50 000 монтарних активних запитів — з великим запасом
   для метаданих книг).
2. Дочекайся, поки проєкт розгорнеться (~2 хвилини).
3. **SQL Editor** (ліва панель) → **New query** → встав увесь вміст `supabase/schema.sql` із
   цього репозиторію → **Run**. Скрипт ідемпотентний (`create ... if not exists`/
   `create or replace`) — його можна перезапускати безпечно, якщо щось знадобиться оновити.
4. **Project Settings → API** → скопіюй **Project URL** і **anon / public** ключ (НЕ
   `service_role` — той ніколи не повинен потрапити в клієнтський застосунок).
5. Встав їх у свій `.env` (не в `.env.example` — той лишається шаблоном без реальних значень):
   ```
   EXPO_PUBLIC_SUPABASE_URL=https://xxxxxxxxxxxx.supabase.co
   EXPO_PUBLIC_SUPABASE_ANON_KEY=eyJhbGc...
   ```
6. Перезапусти Metro/dev-сервер (змінні `EXPO_PUBLIC_*` вбудовуються під час збірки —
   заміна `.env` без перезапуску не підхоплюється).

Без кроків 4-6 застосунок працює точно так само, як до Milestone 8.2 — `SharedCatalogProvider.isEnabled`
рахується з наявності обох змінних, без них поводиться як звичайний вимкнений провайдер.

## Модель безпеки/доступу

Застосунок поки без акаунтів (`docs/LOCAL_FIRST.md`), тож anon-ключ Supabase — публічний за
дизайном (вбудований у клієнтський застосунок, як і в будь-якому Supabase-проєкті). Увесь
реальний захист — на боці бекенду (`supabase/schema.sql`):

- Обидві таблиці (`catalog_book`, `catalog_book_device`) мають `ROW LEVEL SECURITY` увімкнено
  БЕЗ жодної policy (= заборонено все, чого явно не дозволено) і додатково явно відкликані всі
  table-level права в `anon`/`authenticated`. Прямий `SELECT`/`INSERT`/`UPDATE`/`DELETE` з
  клієнта неможливий у принципі.
- Єдиний дозволений шлях — п'ять вузьких `SECURITY DEFINER` RPC-функцій, кожна робить рівно
  одну дію (пошук, лукап за ISBN, апсерт підтверджених метаданих, позначити/зняти позначку
  "додано"). Жодна з них не дає довільного читання/запису поза цим.
- Базові `CHECK`-обмеження (довжина полів, обов'язковість ISBN/назви) — дешевий перший
  рубіж проти зовсім сміттєвих записів, не повний захист від навмисного зловживання.

**Свідомо не зроблено (поки що)**: без власної системи акаунтів немає способу відрізнити
"чесного" клієнта від зловмисника з тим самим (публічним за дизайном) anon-ключем —
теоретично можливий спам записів через ручний виклик RPC в обхід застосунку. Якщо це стане
реальною проблемою на практиці — наступний крок: Supabase Anonymous Auth (безкоштовна опція,
не вимагає форми реєстрації від користувача, але додає rate-limit і трасування зловживань на
рівні окремої анонімної сесії) замість повністю відкритого anon-ключа. Не реалізовано зараз,
бо ризик наразі гіпотетичний, а складність — реальна.

## Схема

Повний, актуальний DDL — `supabase/schema.sql` (єдине джерело правди, не дублюється тут).
Коротко: `catalog_book` (одна книга/видання за ISBN) + `catalog_book_device` (анонімні
позначки "додав собі", основа для `added_count`) + 7 RPC-функцій (`catalog_search`,
`catalog_find_by_isbn`, `catalog_upsert_book`, `catalog_mark_added`, `catalog_mark_removed`,
`catalog_set_cover_if_missing` — Milestone 10, докладніше в розділі нижче;
`catalog_top_books` — Milestone 11, доповнення, розділ "Тренди" нижче).

## «Тренди» (Milestone 11, доповнення)

Пряме прохання власника продукту: топ-10 книг за кількістю РІЗНИХ пристроїв, що зберегли їх
собі в бібліотеку — щоб було видно, що зараз популярніше додають. `catalog_top_books(p_limit)`
— та сама анонімна агрегація `catalog_book_device`, що вже рахує `added_count` для бейджа в
звичайному пошуку (розділ "Пріоритизація в результатах пошуку" нижче), лише як окремий
відсортований список (`order by added_count desc, last_seen_at desc`) замість побічного поля
результату пошуку. Жодної нової таблиці не знадобилось. Клієнт — `SharedCatalogClient.topBooks`
(`src/data/remote/sharedCatalogClient.ts`) → `useTrendingBooks`
(`src/features/trends/useTrendingBooks.ts`) → `app/trends.tsx`.

Свідомо НЕ бере участі кураторська добірка (`curated_book`, `docs/BOOK_PROVIDERS.md`) — вона
не пов'язана з `catalog_book_device`, тож просто не могла б туди потрапити навіть теоретично.
Це навмисно: «Тренди» мають лишатись сигналом органічного вибору справжніх користувачів, а
не тим, що порадив алгоритм рекомендацій.

## Клієнтська інтеграція

- `src/data/remote/sharedCatalogClient.ts` — низькорівневий `fetch`-клієнт до PostgREST RPC
  (той самий підхід, що й `ISBNdbProvider.ts`, без `@supabase/supabase-js` SDK — не потрібен
  для простих RPC-викликів, і не додає нової залежності).
- `src/data/providers/SharedCatalogProvider.ts` — реалізує `BookMetadataProvider`
  (docs/BOOK_PROVIDERS.md), тож безкоштовно перевикористовує весь наявний UI пошуку/ISBN-скану.
  Перший у порядку показу/перевірки — дешевший і швидший за будь-яке зовнішнє джерело.
- `src/data/remote/catalogSync.ts` — фонові (fire-and-forget) записи: публікація підтверджених
  метаданих після успішного збереження книги (`useCreateBookDraft`) і позначки
  "додано"/"прибрано" з бібліотеки (`useAddToLibrary`/`useRemoveFromLibrary`). Жодна з них не
  впливає на те, що бачить користувач — локальна дія лишається єдиним джерелом правди для UI.
- `src/lib/deviceId.ts` — анонімний UUID пристрою (`expo-secure-store`, той самий підхід, що
  й `themePreferenceStorage.ts`), потрібен лише для дедуплікації `added_count`.

## Пріоритизація в результатах пошуку

Пряме прохання користувача: книги, які хтось УЖЕ реально додав собі в бібліотеку, мають йти
першими. `catalog_search`/`catalog_find_by_isbn` рахують `added_count` "на льоту" (не окремим
стовпцем, щоб не міг розсинхронитись) і сортують `added_count DESC` першим пріоритетом, потім
за релевантністю тексту (`similarity`). У результатах пошуку картка з `addedCount > 0` показує
бейдж ("Хтось уже додав цю книгу" / "Додали собі: N").

## "Додати обкладинку" (Milestone 10) — виняток із `manual`-фільтра, і чому він навмисний

`src/data/remote/catalogSync.ts` навмисно не публікує книги з `sourceType: 'manual'` у
`publishToSharedCatalog` — ручний текстовий ввід ніхто не підтверджував, одрук чи помилка
забруднила б каталог для всіх (докладніше — коментар у самому файлі). "Додати обкладинку"
(`app/cover-photo/[editionId].tsx`) — **окрема функція**, `publishCoverToSharedCatalog`, і
для книг, яких у каталозі ще немає, вона свідомо створює новий запис із тим самим
`sourceType: 'manual'`, а не мовчки пропускає цей випадок. Це відхилення від загального
правила, зроблене прямо на прохання користувача ("...обкладинка закріпиться... і в списку
загальних книг, для зручного пошуку іншими користувачами"), а не недогляд — тож варто
розуміти, чим саме воно обмежене:

- Публікується **повний набір метаданих** (назва, автори, видавництво, рік, опис — усе, що
  на той момент відоме про книгу з локальної БД), не лише сама обкладинка. Причина проста:
  RPC `catalog_upsert_book` не вміє створити рядок каталогу лише з ISBN і URL картинки — рядок
  каталогу вимагає назву, авторів і мову як обов'язкові поля (`supabase/schema.sql`,
  `CHECK`-обмеження). Створити "порожній" запис лише під обкладинку неможливо без окремої,
  ширшої зміни схеми — не зроблено зараз, бо для сценарію "я сфотографував книгу, яку сам
  додав вручну" ці метадані й так уже введені користувачем і, як правило, коректні (людина
  дивиться на книгу в руках, а не вигадує дані).
- Це **вужче**, ніж повне зняття фільтра `manual` для всього застосунку: звичайне ручне
  додавання книги (без фото) і далі НІКОЛИ не публікується в каталог — виняток працює лише
  тоді, коли користувач додатково зробив явну, свідому дію "Додати обкладинку" (окремий
  екран, окреме підтвердження "Використати цю обкладинку").
- Якщо книга з таким ISBN у каталозі вже Є (найчастіше — опублікована автоматично раніше,
  просто без обкладинки), новий запис НЕ створюється: `catalog_set_cover_if_missing` лише
  заповнює порожнє поле `cover_url`, ніколи не перезаписуючи вже наявні метадані чи вже
  наявну обкладинку іншої людини.
- Без ISBN (видання зовсім без ISBN13/ISBN10) синхронізація в каталог не відбувається
  взагалі — той самий інваріант "ISBN — єдиний ключ каталогу", що й для решти файлу.

## ISBNdb — коли справді викликається

Порядок на екрані пошуку (`app/(tabs)/search.tsx`): спільний каталог → Google Books → ISBNdb
(Open Library прибрано з активного пошуку в Milestone 10 fix6, `docs/STATUS_V1.md`). ISBNdb
додатково чекає (`isbndbEnabled` у `SearchScreen`), доки перші два джерела не "осядуть" з
порожнім результатом — тобто книгу справді ніхто не шукав раніше і
безкоштовні джерела її не мають. На екрані сканування ISBN (`app/isbn-scan.tsx`) — ще
простіше: точний ISBN-лукап у спільному каталозі перевіряється одразу після локальної бази,
ДО будь-якого зовнішнього провайдера (не лише ISBNdb) — якщо книгу вже підтверджував хтось
інший, жоден зовнішній запит не робиться взагалі.
