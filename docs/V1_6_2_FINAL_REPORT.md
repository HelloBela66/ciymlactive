## 1. Що було реалізовано

### 1.1 Календар — візуальна композиція та redesign дня читання (найімовірніше #160-164, частково)

UI/візуальна фаза поверх Календаря 2.0 (Фаза 19, попередній milestone) — день-клітинка й Day
Details перероблені як "візуальна історія читання" (обкладинка(и) + компактна метрика часу), без
нової персистентної таблиці. Новий cover-стек (`CalendarBookStack` — 1 книга/2
primary+secondary/3+ з бейджем "+N"), нове форматування тривалості, топ-3 книги місяця, повністю
перебудований `app/day/[date].tsx` (hero-підсумок → книги дня → сесії → початок/завершення через
`ReadingRun` → збережено цього дня, spoiler-safe → інша активність). Живий прогін на машині
власника продукту: `tsc` — 0 помилок, `npm test` — 67 test suites/861 тестів, `eslint` — 0
попереджень. Відоме, звітоване й НЕ виправлене цією фазою обмеження: розбіжність soft-delete-
обізнаності між сіткою місяця й деталями дня (успадкована з Фази 19, той самий клас бага, що
Фаза 28 попереднього milestone'у виправила для Бібліотеки, але не для Календаря). Докладніше —
`docs/CALENDAR_VISUAL_REDESIGN_REPORT.md`, чек-лист — `docs/CALENDAR_VISUAL_MANUAL_TEST.md`.

### 1.2 Імпорт власного каталогу книг (найімовірніше #160-164, частково)

Повний, тестований, ідемпотентний CLI-пайплайн (`scripts/catalog-import/*`,
`scripts/sync-curated-books.js`): `data/curated-books.csv` → валідація → нормалізація →
дедуплікація (в межах файлу, за id/ISBN) → завантаження обкладинки на власний Storage (не
посилання на сторонні сайти) → upsert у `curated_book` через `service_role` (обходить RLS без
окремої RPC). Жодної нової таблиці/RPC/npm-залежності — використано вже наявні
`curated_book`/`book-covers` bucket/контрольовані словники. Обов'язковий dry run перед `--apply`;
~26 кодів помилок/попереджень з severity; помилки блокують рядок, попередження — ні. Повторний
запуск того самого CSV — без дублікатів і без повторного завантаження обкладинок; `is_active=false`
замість видалення рядка. Додані книги з'являються у звичайному пошуку без жодної зміни коду
застосунку. Перевірено на реальних 2094 рядках `data/curated-books.csv`. Докладніше —
`docs/OWN_CATALOG_IMPORT.md` (формат/архітектура), `docs/OWN_CATALOG_IMPORT_REPORT.md`
(результат).

**Застереження щодо 1.1/1.2:** `CHANGELOG.md` не має окремих заголовків "#160"…"#164" для жодної з
цих двох робіт — обидві реально зроблені й задокументовані (підтверджено власником продукту), але
точне зіставлення "яка з 5 задач яким конкретно пунктом ТЗ була" в репозиторії не збереглося.
Опис вище — консолідований, за фактичним обсягом зробленого, не по номерах ТЗ.

### 1.5 #167 — Reading Seasons redefinition

Сезон (`app/seasons/[seasonKey].tsx`) — санкціонований ТЗ редизайн з дашборду статистики на
"емоційну пам'ять": головний вміст тепер обкладинки прочитаних книг, улюблена книга, цитата,
збережені думки щоденника (компактні цифри лишаються, але вже не головні). Три реальні
виправлення попутно: прив'язка книги до сезону тепер через `ReadingRun` (не поточний
`UserBook.status`), витяг журналу для картки сезону більше не витікає приватний текст нотатки,
зимова мітка року виправлена на "Зима 2026/27" (був некоректний "Зима 2027"). Докладніше —
`docs/READING_SEASONS.md` (повністю замінює опис Фази 13).

### 1.7 #169 — Home context suppression + Book Details IA polish

### 1.8 #170 — Versioning, npm audit review, CI annotation triage (з власним самовиправленням)

Версія (`0.1.0`) підтверджена як свідоме, вже задокументоване рішення — без змін. Реальний прогін
`npm audit`: 20 moderate vulnerabilities, два ланцюжки без чистого фіксу в межах поточного Expo
SDK (докладніше §5 нижче). CI-анотація "зелено, але з попередженням" root-caused до
`expo-doctor` (нативні теки поруч із полями `app.config.ts`, не регресія).

**Помилка цієї фази, знайдена й виправлена в тому ж #170:** `zustand` спершу помилково прибрано з
`package.json` як "неприбраний код" — перевірка велась по неповній локальній копії репозиторію без
`src/stores/importDraftStore.ts` (реальне використання). CI (`Typecheck, lint, tests`) одразу
впіймав видалення на комміті `bc7b189` — залежність повернуто окремим коммітом `5395bcf`.
Паралельно виявлено й закрито непов'язану, раніше існуючу прогалину: `expo-network` реально
використовувався в коді (`useIsOffline`), але не був у `package.json`. Обидва випадки — нагадування
чому такі перевірки мають йти по живому стану репозиторію, а не по локальному кешу.

### 1.9 Фаза 1/2/3 — Reading Run integrity (`docs/READING_RUN.md`, `docs/BACKUP_FORMAT.md`)

**Фаза 1 (P0):** старт читання лишав книгу з активним `reading_run`, але суперечливим статусом
(`legacy_contradictory_status` у Data Doctor). `ReadingSessionRepository.start()` тепер атомарно
виставляє статус у тій самій транзакції. **Фаза 2:** Фаза 1 зробила видимою суміжну прогалину —
скасування щойно створеної спроби читання лишало run `in_progress` назавжди; `
computeStatusAfterRunRemoval()` коректно повертає і run, і статус книги до стану "як якби спроби
не було", не чіпаючи реальну історію. **Фаза 3:** відновлення бекапу тепер звітує реальний
прогрес (не невизначений спінер); одразу після відновлення — одноразова автоматична перевірка
цілісності з `Alert` на знайдені проблеми.

## 3. Відомі обмеження / залишкові ризики (не виправлені цим циклом, свідомо)

- **Ручна перевірка на реальному пристрої відсутня для всього циклу** — жодна з хмарних сесій не
  мала доступу до фізичного пристрою/емулятора. `docs/OWNER_MANUAL_TEST_LOG.md` (#171) і два
  попередні чек-листи (`docs/CALENDAR_VISUAL_MANUAL_TEST.md`, `docs/MANUAL_UX_TEST_V1_6.md`)
  лишаються повністю непозначеними — це ЄДИНА перевірка, що лишається суто ручною
  (`docs/FINAL_OWNER_ACCEPTANCE_FLOW.md`, зроблений у V1.6.1, лишається чинним для наскрізного
  регресу всього продукту — V1.6.2 не чіпав жодного з 34 його пунктів).
- **npm audit — 20 moderate vulnerabilities**, два ланцюжки: `decode-uri-component` (через
  `query-string`/`@react-navigation`/`expo-router`, фіксу немає) і `uuid <11.1.1` (через
  `@expo/ngrok`/`xcode`, фікс тягне відкат Expo SDK 57→46). Обидва — build/dev-tooling, не шлях
  даних користувача. Докладніше — `docs/SECURITY.md` §3.
- **Календар: розбіжність soft-delete-обізнаності** між місяць-сіткою і деталями дня (§1.1) —
  звітована, поза скоупом цієї фази ("не альтерувати `ReadingRun`-lifecycle").
- **`google-books-proxy` досі не задеплоєний** — код готовий з V1.6.1 Фаза 4, лишається OWNER
  ACTION REQUIRED (успадковано з V1.6.1, цей цикл не чіпав).
- **IP-based rate limiting на трьох Edge Functions** — успадковано з V1.6.1, не адресовано цим
  циклом.
- **Точне зіставлення #160-164 з конкретними задачами ТЗ втрачене** (§1.1/1.2) — сама робота
  реальна й задокументована, лише нумерація не збереглася в CHANGELOG.
