# DNF_IMPROVEMENT.md — «Не дочитав» (Фаза 12)

POLYTSIA V1.6, Фаза 12 (DNF IMPROVEMENT). Цей документ фіксує точну поведінку фічі й
архітектурне рішення, яке інакше довелось би пояснювати заново при кожній фазі (той самий
підхід, що й `docs/SPOILER_SAFE.md`/`docs/PERSONAL_LORE.md`/`docs/BEFORE_AFTER.md`).

## Мета

ТЗ Фази 12: коли книга отримує статус "Не дочитав", дозволь необов'язково зафіксувати причину —
з фіксованого списку або довільним текстом — і збережи це разом зі сторінкою/прогресом і датою
для можливого майбутнього використання в recommendation engine.

## UX-принцип

> DNF не є failure. Microcopy повинна бути neutral. Наприклад: «Не кожна книга має бути
> дочитана». Не використовуй broken streak/negative achievement.

Це визначило все: жодного попереджувального кольору, жодної "сумної" ілюстрації, жодного
обов'язкового поля. Статус міняється тим самим чипом `LibrarySection`, що й будь-який інший —
DNF нічим не виділений серед решти статусів на рівні самого перемикача. Секція "Не дочитав" на
Book Details — це запрошення, а не форма-перешкода: усе в ній можна проігнорувати назавжди.

## Архітектура

### Схема

```sql
CREATE TABLE dnf_reflection (
  id TEXT PRIMARY KEY,
  user_book_id TEXT NOT NULL UNIQUE REFERENCES user_book(id) ON DELETE CASCADE,
  page INTEGER NOT NULL,
  reason TEXT,
  note TEXT,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
```

Ключові рішення:

1. **Рядок створюється автоматично, не формою.** На відміну від `pre_reading_reflection` (де
   перший запис — це `upsert`, який ІНІЦІЮЄ користувач), `dnf_reflection` з'являється сам, у
   мить переходу статусу книги в "Не дочитав" — `DnfReflectionRepository.captureIfMissing`,
   викликана всередині `useUpdateUserBookStatus` (`src/features/library/useUpdateUserBook.ts`),
   тим самим потоком, що вже виставляє `started_at`/`finished_at` у `UserBookRepository.
   updateStatus`. Це і є "date" з ТЗ ("Зберігай: page/progress; date; reason; note") — момент,
   коли книгу залишили, а не момент, коли хтось повернувся дописати деталі.
2. **`page` — `NOT NULL`.** На відміну від `lore_entity.first_seen_page` (де користувач міг і не
   вказати сторінку), тут сторінка ЗАВЖДИ відома — це знімок уже наявного
   `user_book.current_page` (сам `NOT NULL INTEGER` з дефолтом 0), взятий програмно, а не
   введений вручну. Тому немає окремої колонки `progress_percent`: відсоток для показу
   рахується на льоту з `page`/`pageCount` видання (`computeDnfProgressPercent`,
   `src/lib/dnfReflection.ts`, обгортка над тим самим `computeProgressPercent`, що й решта
   застосунку).
3. **`page`/`created_at` фіксуються рівно один раз.** Повторний перехід у той самий статус (чи
   вихід і повернення в DNF пізніше) НЕ перезаписує вже наявний рядок —
   `DnfReflectionRepository.captureIfMissing` перевіряє наявність перед вставкою. Той самий
   "не переписуємо заднім числом" дух, що й `user_book.started_at`/`finished_at`.
4. **`reason` — вільний `TEXT` без CHECK.** Фіксований список (рівно сім причин ТЗ, і в тому ж
   порядку) живе лише на рівні TypeScript — `DnfReasonId`/`DNF_REASON_META`/`DNF_REASON_ORDER`
   (`src/design/dnfReason.ts`) — той самий "не потрібна нова міграція заради нового значення"
   підхід, що й `lore_entity.type`/`note.reaction`.
5. **`note` — окреме поле, незалежне від `reason`.** ТЗ: "Optional free text" — не прив'язане до
   конкретної причини (навіть до "Інше"): користувач може лишити нотатку взагалі без вибору
   причини, обрати причину без нотатки, чи і те, і те.
6. **`reason`/`note` редагуються, `page`/`created_at` — ні.** `DnfReflectionRepository.
   updateDetails` міняє лише `reason`/`note` (+ `updated_at`); немає way оновити `page` заднім
   числом — це б підважило сенс "де я був, коли покинув книгу".
7. **Немає повного видалення з UI.** На відміну від `pre_reading_reflection` (де
   `useRemovePreReadingReflection` прибирає нотатку цілком), тут навмисно немає такої дії —
   `reason`/`note` можна очистити (зберегти форму з порожніми полями), але сам факт "книгу
   покинули на сторінці N такого числа" — DNF MEMORY з ТЗ — лишається назавжди, поки існує
   `user_book`. Видалення всього рядка залишилось у репозиторії (`remove`) лише для
   `ON DELETE CASCADE`-симетрії з рештою memory-таблиць і для тестів, UI його не викликає.

### Причини (`DnfReasonId`)

Рівно сім, у порядку ТЗ: «Не мій настрій», «Нудно», «Не сподобався стиль», «Занадто складно»,
«Не мій жанр», «Повернуся пізніше», «Інше» (`src/design/dnfReason.ts`). `ChipSelect` (той самий
UI-компонент, що й вибір типу лору/статусу) використовується з типом `DnfReasonId | ''`, де `''`
— сентинел "нічого не обрано": на відміну від статусу читання (де завжди є чинне значення),
причина DNF за задумом необов'язкова, а `ChipSelect` завжди показує рівно один вибраний чип
із заданого списку — `''` просто не збігається з жодним варіантом списку, тож жоден чип не
підсвічується, доки користувач сам щось не натисне.

### Екран

Секція "Не дочитав" — `app/work/[workId].tsx`, одразу після "До читання" (`PreReadingReflection
Section`). Видима лише коли `dnf_reflection` уже існує для книги (тобто статус хоч раз був "Не
дочитав") — для книги, яка ніколи туди не переходила, секції просто немає. Форма редагування
причини/нотатки доступна лише поки статус РЕАЛЬНО "Не дочитав" (`canEditDnfReflection`); сам
запис (сторінка, дата, причина, нотатка) лишається видимим і після зміни статусу — той самий
"read-only спогад" підхід, що й `PreReadingReflectionSection` після завершення читання. Коли
причина й нотатка ще порожні, замість форми-перешкоди показується нейтральний текст ТЗ: «Не
кожна книга має бути дочитана.»

## DNF MEMORY і майбутнє

ТЗ: "Це потім може використовуватись у recommendation engine." Ніякого recommendation engine у
цій фазі немає — `dnf_reflection` лише зберігає структуровані дані (сторінка/прогрес, дата,
причина, нотатка) в тому вигляді, який майбутня фіча зможе прочитати без повторної міграції.

## Бекап

`dnf_reflection` — реальні дані користувача, входить у `BACKUP_TABLE_ORDER`
(`BackupRepository.ts`) одразу після `pre_reading_reflection` (той самий сусід `user_book`,
лише реальний FK, уже присутній раніше в масиві).

## Приватність

Жодних мережевих викликів, жодного AI/LLM-аналізу — той самий принцип, що й решта memory-фіч
(`docs/BOOK_CAPSULES.md` §Приватність). "Recommendation engine" з ТЗ — гіпотетична майбутня
локальна фіча, а не натяк на аналіз даних десь ззовні.
