Знахідка 🔴 нижче ("Платний ключ ISBNdb іде прямо в клієнтський білд") — **виправлено в коді**.
Архітектура: `Мобільний застосунок → supabase/functions/isbndb-proxy/ (Supabase Edge Function)
→ ISBNdb`. Деталі:

- `src/data/providers/ISBNdbProvider.ts` більше НІКОЛИ не звертається до `api2.isbndb.com`
  напряму й не читає жодного ISBNdb-ключа з `process.env` — увесь мережевий виклик іде через
  новий `src/data/remote/isbndbProxyClient.ts`, до `${SUPABASE_URL}/functions/v1/isbndb-proxy`.
- Сам ключ (`ISBNDB_API_KEY`) живе виключно як Supabase secret (`supabase secrets set
  ISBNDB_API_KEY=...`) — ніколи `EXPO_PUBLIC_*`, ніколи в бандлі, ніколи в git. Докладна
  інструкція розгортання — `supabase/functions/isbndb-proxy/README.md`.
- Проксі-функція (`index.ts` поруч) додає: валідацію тіла запиту (`op: 'search' | 'lookup'`),
  межі довжини пошукового запиту (2–200 символів), повну перевірку контрольної цифри ISBN
  перед лукапом (`isbn.ts`, навмисна часткова копія `src/lib/isbn.ts` — Deno-рантайм Edge
  Function не бачить `src/` мобільного застосунку), таймаут запиту до ISBNdb (8с), жорстку
  межу розміру відповіді (2 МБ, реальний підрахунок байтів під час стріму, не лише довіра
  `Content-Length`), і нормалізовані помилки (`{ error, code }`, коди на кшталт
  `bad_request`/`timeout`/`upstream_error`/`rate_limited`).
- Клієнт (мобільний застосунок) отримує ЛИШЕ нормалізовану форму книги (той самий склад
  полів, що й `RawProviderBook`) — жодних службових полів ISBNdb (`binding`, `dewey_decimal`,
  `msrp` тощо) і, звісно, жодного секрету.
- **Rate limiting (пре-Auth компроміс, задокументований свідомо):** без Supabase Auth немає
  стабільного "хто саме" — реалізовано ліміт за IP-адресою клієнта, durable (переживає
  холодний старт інстансу функції) через нову таблицю/RPC `edge_rate_limit`/
  `edge_rate_limit_check` у `supabase/schema.sql`. Два вікна: 20 запитів/60с (burst) і 300
  запитів/добу (sustained) на IP. Поверх цього — платформна перевірка Supabase JWT
  (`verify_jwt` лишається увімкненим за замовчуванням для функції) відсікає найпростіше
  анонімне сканування ще до виконання коду функції.
  **Залишковий ризик:** IP — недосконалий ідентифікатор (спільний NAT/мобільний оператор
  об'єднує кількох реальних користувачів під одним IP; зловмисник із VPN отримує новий IP на
  вимогу). Це найкращий безпечний pre-auth варіант, не гарантія — справжній per-користувач
  ліміт вимагає Supabase Auth, свідомо поза межами цього milestone (`POLYTSIA V1.5`,
  "DO NOT IMPLEMENT YET").
- `isEnabled` провайдера тепер — окремий, явний, НЕ секретний прапорець
  `EXPO_PUBLIC_ISBNDB_PROXY_ENABLED` (просто "0"/"1") + перевірка налаштованого Supabase —
  зберігає той самий свідомий "платне джерело вмикається окремо" принцип, що діяв і раніше.
- **✅ Розгорнуто й перевірено (2026-09-10).** Власник продукту виконав усі кроки вище
  (деплой, секрет, `schema.sql`, прапорець в `.env`) і перевірив функцію напряму —
  `{"op":"lookup","isbn":"..."}` і `{"op":"search","query":"..."}` (англомовний запит)
  обидва повернули реальні дані з ISBNdb. Перший тест пошуку кириличним запитом дав порожній
  результат — виявилось артефактом кодової сторінки консолі PowerShell 5.1 (кирилиця

  підтверджено повторним тестом англомовним запитом. Додано постійне діагностичне логування

  подібних випадків без повторного редеплою.

## Оновлення (2026-09-10) — Фаза 1.2: `book-covers` більше не приймає анонімний запис напряму

Знахідка 🟡 нижче — **виправлено в коді**. Архітектура: `Мобільний застосунок →
supabase/functions/cover-upload/ (Supabase Edge Function) → Supabase Storage`.

- `supabase/schema.sql`: policy `"book-covers anon upload"` (дозволяла `anon`/`authenticated`
  необмежений `INSERT` у bucket) — **видалено повністю**. RLS на `storage.objects` для цього
  bucket тепер deny-all для прямого клієнтського запису, той самий принцип, що й
  `catalog_book`/`curated_book`/`edge_rate_limit`. Читання (`public: true` на самому bucket)
  лишається відкритим навмисно — небезпечним був запис, не читання.
- `src/data/remote/coverStorageClient.ts` більше не пише в Storage напряму anon-ключем — шле
  байти зображення в `cover-upload` Edge Function, яка сама перевіряє реальний тип файлу за
  magic bytes (не лише заявлений `Content-Type`, який тривіально підмінити), обмежує розмір
  (5 МБ, реальний підрахунок байтів під час стріму), і, найважливіше, **сама генерує шлях
  об'єкта** (`crypto.randomUUID()` + розширення за реальним типом) — жодного клієнтського
  рядка (раніше — `editionId` + `Date.now()` з `app/cover-photo/[editionId].tsx`) у шляху
  сховища взагалі. Це прибирає одночасно і "довільний шлях у bucket", і path traversal —
  конструктивно, не перевіркою вхідних даних.
- Rate limiting — той самий механізм, що й `isbndb-proxy` (спільна таблиця/RPC
  `edge_rate_limit`), окремий, щедріший ліміт (10 запитів/60с, 100/добу на IP — тут ризик не
  пряма оплата за запит, а вичерпання квоти сховища/трафіку). Той самий залишковий ризик
  IP-based rate limiting, що й для ISBNdb-проксі вище.
- **✅ Розгорнуто й перевірено (2026-09-10).** Власник продукту задеплоїв функцію, застосував
  `schema.sql` і перевірив обидва факти безпосередньо в SQL Editor: `select policyname from
  pg_policies where tablename = 'objects' and schemaname = 'storage'` повернув 0 рядків (стара
  policy `"book-covers anon upload"` дійсно відсутня — жодного прямого клієнтського запису в
  bucket більше не дозволено), `select to_regclass('public.edge_rate_limit')` підтвердив
  таблицю rate limit. Реальний виклик функції з байтами PNG повернув `{"url":
  ".../book-covers/<uuid>.png", "path": "<uuid>.png"}` — шлях об'єкта справді випадковий UUID
  від сервера (не клієнтський рядок), файл справді завантажився й відкривається за публічним
  URL.

Обидві знахідки цього аудиту (🔴 і 🟡) виправлено, задеплоєно й перевірено на реальних
викликах — Фаза 1 (Security P0) milestone «POLYTSIA V1.5» повністю завершена, без жодного
відкритого пункту.

оплата за запит.

- `src/data/providers/GoogleBooksProvider.ts` більше НІКОЛИ не читає

  лише тепер це єдиний шлях без проксі, а не "деградація без ключа" поруч зі "звичайний режим
  із ключем у бандлі").
- Сам ключ (`GOOGLE_BOOKS_API_KEY`, опційний) живе лише як Supabase secret
  (`supabase secrets set GOOGLE_BOOKS_API_KEY=...`) — ніколи `EXPO_PUBLIC_*`. Докладна
  інструкція розгортання — `supabase/functions/google-books-proxy/README.md`.
- Проксі-функція (`index.ts` поруч) — той самий каркас захисту, що й `isbndb-proxy`: валідація
  тіла запиту (`op: 'search' | 'lookup' | 'get_edition'`), межі довжини пошукового запиту

  GOOGLE_BOOKS_PROXY_ENABLED` — той самий "0"/"1" power-switch патерн, що й ISBNdb, але з
  протилежною семантикою вимкненого стану: тут це "без підвищеної квоти", не "джерело

## 1. Реальні знахідки

### 🔴 → ⚪ Платний ключ ISBNdb іде прямо в клієнтський білд, викликається з пристрою напряму

**Виправлено (2026-09-10, Фаза 1.1 вище).** Історичний опис проблеми — для контексту:

`src/data/providers/ISBNdbProvider.ts` відправляв `Authorization: API_KEY` прямо з `fetch()`
у застосунку, а сам ключ — `EXPO_PUBLIC_ISBNDB_API_KEY`, Expo public env var, який
компілювався буквально в JS-бандл. Будь-хто, хто розпакує зібраний застосунок (тривіально —
`strings` на APK/IPA чи розпакований JS-бандл), діставав реальний ключ ISBNdb і міг робити
необмежену кількість платних запитів від імені акаунту власника (тарифи ISBNdb стартують від
$14.99/міс за 5000 запитів/день) — без жодної прив'язки до конкретного пристрою чи способу
заблокувати конкретного викликача, крім ротації ключа (яка ламає застосунок для всіх, доки не
вийде новий білд).

Це принципово інша ситуація, ніж Supabase anon-ключ (той навмисно публічний — бекенд сам
захищає доступ через RLS+RPC, ключ без бекенд-перевірки нічого не дає). У ISBNdb такого шлюзу
не було — сам ключ і був авторизацією.

**Фікс:** тонка Supabase Edge Function (`supabase/functions/isbndb-proxy/`), яка тримає
ISBNdb-ключ на сервері й проксує лише два виклики, які реально потрібні застосунку (пошук за
назвою/автором, пошук за ISBN) — той самий патерн, що вже використовувався для RPC спільного
каталогу.

### 🟡 → ⚪ Supabase Storage bucket `book-covers` приймав необмежену кількість анонімних завантажень

**Виправлено (2026-09-10, Фаза 1.2 вище).** Історичний опис проблеми — для контексту:

`supabase/schema.sql` давав `anon`/`authenticated` необмежений `INSERT` у сховище обкладинок
(заборонені лише `UPDATE`/`DELETE`). Перевірка "≤5MB, jpeg/png" — це фільтр вмісту, не ліміт
обсягу. Будь-хто з anon-ключем (який неминуче публічний) міг скриптом заливати 5MB-файли в
циклі — вичерпує квоту сховища й генерує рахунок за трафік/зберігання, без жодного
per-пристрій обмеження в схемі.

**Фікс:** Edge Function `supabase/functions/cover-upload/` — той самий шлюз-патерн, що й для
ISBNdb вище.

### 🟡 → ⚪ Ключ Google Books іде прямо в клієнтський білд

**Виправлено (2026-09-13, Фаза 4 вище).** Історичний опис проблеми — для контексту:

`src/data/providers/GoogleBooksProvider.ts` читав необов'язковий
`EXPO_PUBLIC_GOOGLE_BOOKS_API_KEY` (Expo public env var) і додавав його до кожного прямого
клієнтського запиту до `www.googleapis.com/books/v1` — той самий компіляційний-у-бандл ризик,
що й ISBNdb вище (`strings` на зібраному APK/IPA чи розпакованому JS-бандлі дістає ключ),
**але з принципово нижчим ступенем ризику, ніж ISBNdb**: Google Books API безкоштовний,
ключ лише піднімає квоту (не умова роботи взагалі), тож витік не дає зловмиснику прямого
доступу до платного ресурсу — щонайбільше дозволяє вичерпати квоту власника продукту,
знизивши сервіс для реальних користувачів застосунку до анонімного рівня. Саме тому ця
знахідка від самого початку класифікована 🟡 (середній пріоритет), не 🔴.

**Фікс:** та сама Edge Function-проксі архітектура, що й для ISBNdb (`supabase/functions/
google-books-proxy/`), з нюансом "секрет опційний, деградація graceful" — докладніше розділ
"Оновлення (2026-09-13)" вище.

## 2. Перевірено й підтверджено коректним

- **SQL injection.** Жоден repository не будує SQL з даних, що можуть прийти з мережі
  (Google Books/ISBNdb/спільний каталог) — усі значення йдуть через `?`-плейсхолдери.
  `BackupRepository.ts` інтерполює назви таблиць/колонок напряму в SQL, але назви таблиць
  завжди беруться з жорстко заданого `BACKUP_TABLE_ORDER`, ніколи з ключів розпарсеного
  JSON, а назви колонок додатково фільтруються регексом `^[a-zA-Z_][a-zA-Z0-9_]*$` — навіть
  повністю ворожий файл бекапу не може підмінити назву таблиці/колонки.
- **Supabase RLS/RPC.** Усі чотири таблиці (`catalog_book`, `catalog_book_device`,
  `curated_book`, і, з Фази 1.1 вище, `edge_rate_limit`) мають RLS увімкнено й ЖОДНОЇ policy
  (deny-all) плюс явний `revoke all from anon, authenticated` — прямий доступ до таблиць
  неможливий незалежно від витоку anon-ключа. Усі RPC типізовані (`text[]`/`text`/`uuid`),
  жодної динамічної побудови SQL всередині — без SQL injection поверхні.
  `catalog_upsert_book`/`catalog_set_cover_if_missing` не дають клієнту перезаписати чужий
  запис каталогу чи видалити чиїсь дані. `curated_book` — на крок суворіше: для неї немає
  ЖОДНОЇ write-RPC взагалі (лише 4 read-only RPC). `edge_rate_limit` — ще на крок суворіше за
  `curated_book`: жодного `grant` навіть на RPC для `anon`/`authenticated` узагалі, лише
  `service_role` (викликається виключно з коду самої Edge Function, ніколи з клієнта).
- **Секрети.** Жодного хардкодженого секрету ніде в коді. `.env.example` — порожні значення
  з коментарями. Усі `process.env.*` в клієнтському коді (усе, що потрапляє в бандл Expo) —
  виключно `EXPO_PUBLIC_*`, і жодне з них (з Фази 1.1 вище — включно з ISBNdb) більше не є
  секретом. `service_role` ключ Supabase ніде в клієнтському коді не згадується — потрібен
  лише окремому Node-скрипту `scripts/sync-curated-books.js` (запис у `curated_book`) і,
  автоматично від самого Supabase (не власником продукту вручну), середовищу Edge Function
  `isbndb-proxy` (виклик `edge_rate_limit_check`). `.env.admin` — окремий, явно (не через
  wildcard) перелічений рядок `.gitignore`, зі своїм шаблоном `.env.admin.example`.
- **Файлова система / шляхи.** `backupFile.ts`/`csvFile.ts` будують імена файлів лише з
  timestamp'ів, ніколи з користувацьких/мережевих рядків. `coverPhotoStorage.ts` будує шляхи

## 3a. CI "зелено, але з анотацією" — POLYTSIA V1.6.2, #170 (джерело знайдено, підтверджено)

Раніше (`docs/V1_6_1_FULL_AUDIT_REPORT.md` §18/§44 та ін.) кілька прогонів CI показували
"Success" на джобі, але панель Annotations — "1 error and N warnings", і це лишалось
незакритою гіпотезою ("ймовірно `continue-on-error`-крок, не перевірено предметно"). Тепер
перевірено предметно, на прогоні #95 (комміт `d9c7fd3`): анотація — виключно з кроку
**"Expo health check (expo-doctor)"** (`ci.yml`, `continue-on-error: true`) —
`npm audit (advisory)` на цьому ж прогоні пройшов БЕЗ помилки (1s, зелена галочка, жодної
анотації). `expo-doctor` знаходить рівно одну реальну, специфічну для цього проєкту умову:
"Check for app config fields that may not be synced in a non-CNG project" — проєкт має і
нативні теки (`android/`, `ios/` — Bare/Prebuild-конфігурація), і нативні поля прямо в
`app.config.ts` (`scheme`/`orientation`/`userInterfaceStyle`/`icon`/`primaryColor`/`ios`/
`android`/`plugins`), а EAS Build НЕ синхронізує ці поля в нативні теки, доки вони існують —
це попередження про архітектурний вибір проєкту (Prebuild з наявними нативними теками), не
про баг чи регрес. `continue-on-error: true` на цьому кроці — правильна поведінка (advisory,
не має валити джобу за відоме, свідоме архітектурне рішення). Змін коду/конфігурації не
потрібно; сама зміна нативної/Prebuild-структури проєкту — поза межами "без реального багу"
(і поза межами цієї документаційної фази).

**Реальний деплой і виклик `isbndb-proxy`/`cover-upload`** — ОНОВЛЕНО (2026-09-10, розділи
"Оновлення" вище): обидві функції задеплоєні й перевірені власником продукту напряму (реальні
HTTP-виклики, підтверджені записи в `pg_policies`/`edge_rate_limit`). Цей пункт більше НЕ
