## 1. TL;DR — якщо читати лише один розділ

- **Що це:** персональна читацька операційна система (не соцмережа, не трекер-мінімалка) —
  один користувач, local-first (SQLite на пристрої), повністю українською, без акаунтів,
  без монетизації. «Полиця — твоя читацька пам'ять.»
- **Скільки зроблено:** весь core loop і **майже весь Milestone 0-11** зі специфікації
  реалізовано й перевірено вручну (частково — на реальному Android-пристрої через EAS-білд).

  через Supabase.
- **Що НЕ зроблено чи не підтверджено:**
  - 🔴 **Відкритий ризик безпеки** — платний ключ ISBNdb іде прямо в клієнтський білд,
    тривіально видобувний, необмежені платні запити від імені власника продукту (розділ 8).
  - **Жоден тест ніколи не прогнаний по-справжньому** — 13 доменних `jest`-тестів написані й
    виглядають коректними при читанні коду, але жодного реального запуску `npx jest` в жодній

  - Немає CI (GitHub Actions чи інше) — усі перевірки корректності досі повністю ручні, на
    машині власника продукту.
  - iOS-білд не робився (немає платного Apple Developer акаунту); Android preview-білд є.
  - `npm audit` показав "19 moderate severity vulnerabilities" на машині власника продукту —

## 2. Продуктова концепція

**Довгострокове бачення:** не трекер, а операційна система читача — одне місце, де живе все,
що людина коли-небудь читала, читає й планує прочитати, разом із контекстом (нотатки, цитати,
час, темп, місце в серії).

**Кому це зараз (V1):** один користувач (власник продукту), кілька місяців щоденного
використання, перевірка продуктової концепції перед інвестицією в багатокористувацькість. Тому
в V1 свідомо немає ні монетизації, ні акаунтів, ні соціальних функцій.

**Core loop** (найважливіший інваріант продукту — кожне UX-рішення оцінюється відносно того, чи
воно стоїть на шляху цього циклу):

```
Відкрив застосунок → Продовжив читання → Читав → Завершив сесію
   → Прогрес збережено → Історія/статистика оновились
```

**Статуси книги** (укр., `src/design/i18n-labels.ts`): Хочу прочитати · Читаю · Прочитано ·
Відкладено · Не дочитав · Перечитую.

**Принципи UX:**
- Найчастіші дії (почати/продовжити читання, оновити прогрес, додати нотатку, знайти книгу,
  змінити статус) — 1 tap, максимум 2.
- Прогресивне розкриття: просте видиме одразу, деталі — за explicit tap "Показати деталі".
- Жодне необов'язкове поле не блокує збереження.
- Конфлікт "більше функцій" vs "якість core loop" завжди вирішується на користь якості.
- Порожні/помилкові стани завжди пропонують дію, а не лише констатують факт; мережеві помилки
  — українською, без технічних деталей, із working fallback (manual entry).

**Свідомо поза межами V1:** підписки, оплата, реклама, соцмережа, друзі, книжкові клуби, чат,
AI-асистент, публічні рецензії, portal видавця, marketplace, recommendation engine, складний
cloud sync, мікросервіси. Архітектура не блокує жодне з цього пізніше (розділ 11).

## 3. Технологічний стек

Expo SDK 57 / React Native 0.86.3 / React 19.2.3, TypeScript `strict: true` (`~6.0.3`), Expo
Router (file-based, typed routes), `expo-sqlite` (async API) з власним migration runner на
`PRAGMA user_version`, TanStack Query 5 (мережевий/спільний стан), Zustand 5 (лише точковий
UI-стан — активний reading timer, фільтр бібліотеки), Zod 4 (валідація зовнішнього вводу),
date-fns 4, `expo-image` (кешовані обкладинки), `expo-notifications` (лише локальні),
`expo-camera` (ISBN-сканер, `CameraView`), `expo-image-picker` (фото обкладинки),
`react-native-view-shot` + `expo-media-library` (експорт картки-спогаду), `@shopify/flash-list`
(віртуалізовані списки), Supabase (лише спільний каталог/кураторська добірка/обкладинки — без
акаунтів, без персональних даних; простий `fetch` до PostgREST RPC, без `@supabase/supabase-js`
SDK).

Свідомо НЕ використовується: Firebase, Redux, GraphQL, WatermelonDB/RxDB.

**Важлива операційна деталь:** увесь код написаний і перевірений вручну в хмарних сесіях
розробки БЕЗ доступу до npm-реєстру — версії пакетів у `package.json` звірені напряму з
`registry.npmjs.org` через веб-пошук (не підібрані за пам'яттю), після того як перший реальний
`npm install` на машині власника продукту виявив кілька версій, що реально не існували. `tsc
--noEmit` реально запускався і знаходив помилки (усі виправлені) лише на машині власника
продукту — ніколи в жодній хмарній сесії розробки. `jest` не запускався ніде й ніколи (розділ
9).

## 4. Архітектура

### 4.1 Шари (feature-based + layered)

```
UI (app/ routes, feature screens, components)
   │ викликає хуки, ніколи не SQL напряму
   ▼
Feature hooks (src/features/*/hooks)
   │ оркеструють кілька repositories/services, тримають React Query cache
   ▼
Domain services (src/domain/*, src/lib/*) — чиста логіка, без React, без SQL,
   без Date.now() напряму (час — параметр, для детермінованих тестів)
   │
   ▼
Repositories (src/data/repositories/*) — єдине місце, що знає SQL
   │
   ▼
DB layer (src/data/db) — connection, migration runner
   ▼
SQLite (пристрій)
```

Правило: компонент екрана ніколи не імпортує `src/data/db` напряму й не містить бізнес-логіки.
Domain-сервіси не імпортують React/Expo — це і є межа, що робить доменну логіку тестованою в
Node без емулятора (хоча реально жоден такий тест ще не прогнаний, розділ 9).

### 4.2 Local-first

SQLite — основне сховище, не кеш перед сервером. Жоден екран core loop (Home, таймер, прогрес,
нотатки) не має мережевого запиту на критичному шляху. Мережа (пошук метаданих книг, спільний
каталог) — необов'язкова надбудова, тихо деградує без Supabase/API-ключів: усі
`isXxxConfigured()`-перевірки повертають `false`/`null` замість кидати виняток.

### 4.3 Provider-модель для метаданих книг

Один інтерфейс `BookMetadataProvider` (`searchBooks`/`lookupByISBN`/`getEdition`/
`normalizeBook`), кілька реалізацій, порядок пошуку (від дешевого до платного):

1. **SharedCatalogProvider** — кеш підтверджених результатів усіх користувачів застосунку у
   власному Supabase (Milestone 8.2). Найдешевший і найшвидший.
2. **CuratedCatalogProvider** — власна база книг власника продукту (Milestone 11, доповнення);
   `data/curated-books.csv` → Supabase `curated_book`, наповнюється ЛИШЕ через `service_role`-
   ключ і `scripts/sync-curated-books.js`, ніколи з клієнта.
3. **GoogleBooksProvider** — офіційний безкоштовний API, з опційним ключем проти rate-limit.
4. **ISBNdbProvider** — платний (від $14.99/міс), останній у черзі, викликається лише коли
   дешевші джерела не дали результату.
5. **ManualBookProvider** — ручне введення, завжди `isEnabled: true`, гарантований fallback.

**OpenLibraryProvider прибраний повністю** (Milestone 10 fix6) — на пряме прохання власника
продукту; `'open_library'` лишається валідним історичним значенням enum для вже збережених
книг. Сім заготовок під українські книгарні (Yakaboo, КСД, BookYe, BookUa, Ranok, NashFormat,
BalkaBook) теж видалені як мертвий код — жоден із цих сайтів не має дозволеного публічного API,
а обхід захисту сайтів (`robots.txt`, CAPTCHA, rate limits) — **жорстке правило проєкту, без
винятків**.

**Українська мовна фільтрація** (Milestone 7.1) — двошарова: (1) `langRestrict=uk` на рівні
запиту до Google Books, де можливо; (2) клієнтський фільтр `isLikelyUkrainianBook` — мовна
мітка від джерела І кирилиця в назві одночасно (захист від випадків на кшталт реального
знайденого запису ISBNdb з `language: 'ukrainian'`, але англомовним title). Для «Що почитати
завтра?» — послаблений каскад рівнів (розділ 7), бо сувора подвійна перевірка інколи відсіювала
геть усі кандидати.

## 5. Дані — модель і сховище

### 5.1 SQLite (пристрій, джерело правди)

24 таблиці, `TEXT` UUID як primary key всюди (не autoincrement — потрібно для майбутньої
синхронізації без конфліктів ID між пристроями), кожна sync-придатна таблиця має
`created_at`/`updated_at`/`deleted_at` (soft delete). Дати — ISO-8601 `TEXT` (UTC). Гроші —
`INTEGER` у мінімальних одиницях.

Ключові групи таблиць:
- **Каталог:** `author`, `publisher`, `translator`, `genre`, `tag`, `work`, `work_author`,
  `work_genre`, `edition`, `edition_translator`, `book_source`, `field_provenance`,
  `tagged_item`.
- **Серії:** `series`, `series_entry` (`position REAL` — дробові для новел).
- **Бібліотека користувача:** `user_book` (статус, поточна сторінка), `shelf`, `shelf_book`.
- **Читання:** `reading_session` (immutable historical record, `paused_intervals` як JSON),
  `reading_progress` (похідні контрольні точки, окремо від сесій — для календаря/pace без
  перерахунку сесій щоразу).
- **Щоденник (Milestone 11):** `note`, `quote` (симетричні поля після Migration 003:
  `progress_percent`/`tags`/`is_favorite`/`reaction`), `note_category`, `journal_draft`
  (чернетка композера, НЕ входить у бекап), `book_memory` («Спогад про книгу» — рефлексія +
  посилання на записи щоденника через `entry_refs` JSON, не копія тексту; один на книгу).
- **Фізична бібліотека:** `owned_book`, `loan`.
- **Цілі/нагадування:** `reading_goal`, `reminder`.
- **Рекомендації (Milestone 11):** `book_recommendation_shown` — локальна історія показаних
  рекомендацій за парою жанр+мета, щоб не повторюватись.
- **Налаштування:** `app_settings` (singleton, `id='local'`).

Історія міграцій — 7 файлів (`001_base_schema` до `007_book_source_curated`), кожна
forward-only, деякі — rebuild-патерн (нова таблиця з потрібним `CHECK` → копія даних →
видалення старої → перейменування, бо SQLite не підтримує `ALTER CHECK` напряму), з
`PRAGMA foreign_keys = OFF/ON` навколо таких кроків.

### 5.2 Supabase (спільна, некритична надбудова)

Три таблиці, усі з RLS увімкнено БЕЗ жодної policy (deny-all) + явний `revoke all from anon,
authenticated` — прямий доступ з клієнта неможливий у принципі, увесь доступ лише через вузькі
`SECURITY DEFINER` RPC:

- `catalog_book` + `catalog_book_device` (Milestone 8.2) — спільний кеш метаданих книг усіх
  користувачів застосунку + анонімний лічильник "додав собі" (ключ — випадковий UUID
  пристрою, без зв'язку з персональними даними). 7 RPC: `catalog_search`,
  `catalog_find_by_isbn`, `catalog_upsert_book`, `catalog_mark_added`, `catalog_mark_removed`,
  `catalog_set_cover_if_missing`, `catalog_top_books` («Тренди»).
- `curated_book` (Milestone 11, доповнення) — кураторська добірка власника продукту. На крок
  суворіше за `catalog_book`: НЕМАЄ жодної write-RPC взагалі, лише 4 read-only
  (`curated_book_search`/`_recommend`/`_find_by_isbn`/`_get`). Єдиний спосіб писати —
  `service_role`-ключ (`.env.admin`, у `.gitignore`) і `scripts/sync-curated-books.js`,
  запускається виключно вручну з терміналу власника продукту.
- Storage bucket `book-covers` — фото обкладинок користувачів, приймає необмежену кількість
  анонімних завантажень (🟡 відкритий ризик, розділ 8).

Джерело правди схеми — `supabase/schema.sql` (ідемпотентний, можна перезапускати безпечно).

### 5.3 Кураторська добірка книг — конвеєр даних

`data/curated-books.csv` (зараз 2038 рядків після сьогоднішнього очищення, розділ 12) →
`scripts/sync-curated-books.js` (Node, без нових залежностей, власний CSV-парсер) →
`curated_book` у Supabase. Колонки: `id` (слаг, первинний ключ — зміна створює НОВИЙ запис, не
оновлює), `title`, `authors`, `isbn13`/`isbn10` (мають бути унікальними по всьому файлу Й по
всій базі — окреме UNIQUE-обмеження, не пов'язане з `id`), `page_count`, `cover_url`,
`description`, `genres` (точні назви зі списку — інакше книга не потрапить у фільтр),
`purposes` (light/cry/laugh/absorbed), `language`, `is_active`. Скрипт валідує й показує
підсумок (додано/оновлено/пропущено з поясненням) — жоден валідний рядок не блокується через
один невалідний, включно з ISBN-конфліктами; мережеві кроки (перевірка наявних `id`/ISBN)
розбиті на пакети по 150 рядків (фікс `HTTP 414`, доповнення18). Новий допоміжний скрипт
`scripts/shorten-long-ids.js` (сьогодні, розділ 12) вкорочує задовгі `id` до прогону sync.

## 7. «Що почитати завтра?» і «Тренди» — деталі (Milestone 11, доповнення)

Обидві фічі — пряме прохання власника продукту, свідомо розв'язані БЕЗ акаунтів (лягають на
вже наявну анонімну інфраструктуру спільного каталогу):

- **«Що почитати завтра?»** (`app/tomorrow.tsx`, `src/lib/tomorrowRecommendation.ts`) — жанр +
  бюджет часу + мета читання (легке проведення часу / поплакати / посміятись / вникнути в
  історію) → одна нова книга, якої ще немає в бібліотеці, без повторів на той самий запит
  (`book_recommendation_shown`). Спершу пробує кураторську добірку (жанр/мета проставлені
  вручну — точний збіг, підтверджена мова, без мережевого пошуку); лише коли для пари
  жанр+мета в добірці ще немає непоказаного кандидата — фолбек на `GoogleBooksProvider` з
  послабленим каскадом мовної фільтрації (`pickLanguageTier`: строгий → лише кирилиця в назві
  → без фільтра, перший непорожній перемагає — бо сувора перевірка інколи відсіювала все).
  `ISBNdbProvider` тут НІКОЛИ не викликається (щоб не множити платний ризик на цю фічу).
- **«Тренди»** (`app/trends.tsx`) — топ-10 книг за кількістю пристроїв, що додали їх собі;
  `catalog_top_books` RPC на вже наявних `catalog_book`/`catalog_book_device`, без нової
  таблиці. Свідомо НЕ бере участі кураторська добірка (окремий сигнал — органічний вибір
  користувачів, не порада алгоритму).

## 9. Тестове покриття — реальний стан (найважливіша прогалина процесу)

13 файлів `src/lib/*.test.ts`/`src/domain/*.test.ts` написані для чистої доменної логіки:
`readingPace`, `finishPrediction`, `tbrEstimate`, `streaks`, `seriesOrdering`,
`backupSerializer`, `sessionTiming`, `bookStats`, `journalInvalidation`, `memoryCardMood`,
`tomorrowRecommendation`, `calendarGrid`, `isbn`, `pluralizeUk`. Усі виглядають коректними при
ручному читанні коду (включно з граничними випадками — сесія через північ, часовий пояс,
`pageCount` пріоритетніший за `currentPage`, `rng`-ін'єкція для детермінованої перевірки
навмисно недетермінованого вибору тощо) — **але жоден із них жодного разу не був реально
прогнаний через `jest`** у жодній хмарній сесії розробки (немає доступу до npm-реєстру в
цьому середовищі).

**Repository-шар (увесь реальний SQL — десятки методів, JOIN'и, includно з `countsByReaction`,
який щойно виправляли) не має ЖОДНОГО автоматизованого тесту**, хоча `docs/TESTING.md` описує
такий шар ("Repository-тести, інтеграційні, проти реального `expo-sqlite`") як задуманий.

Немає CI взагалі — жоден push/PR не запускає `tsc --noEmit`/`jest`/`eslint` автоматично.

**Пряма рекомендація для V2:** налаштувати GitHub Actions (там є доступ до npm-реєстру, на
відміну від середовища розробки, що використовувалось досі), щоб `npm install && npx tsc
--noEmit && npx jest` запускались на кожен push/PR — єдиний спосіб уперше побачити, чи реально
проходять усі 13 тестів, і ловити регресії автоматично, а не покладатись виключно на ручне
тестування власника продукту на реальному пристрої.

## 10. Технічний борг і дрібні відкриті знахідки

Зведено з усіх незалежних аудитів (`STATUS_V1.md` розділи 3/6/8, `V2_READINESS.md` розділ 8).
Переважна більшість реальних знахідок УЖЕ виправлена (нижче — лише те, що залишається
відкритим чи варте уваги):

- **Мертвий код:** `JournalRepository.countAll`/`useJournalGlobalCount()` визначені й
  задокументовані як "картка-вхід на Home + статистика зверху екрана щоденника", але жоден
  екран їх фактично не викликає. Не критично, варто або підключити, або прибрати.
- **`getDeviceId()` (`src/lib/deviceId.ts`)** — рідкісна гонка при першому одночасному виклику
  одразу з двох місць — теоретично може зареєструвати один пристрій під двома різними
  анонімними ID.
- **`ReadingGoalRepository.getProgress`** для цілей "завершити книгу"/"книг на рік" підвантажує
  повні дані ВСІХ прочитаних книг замість легшого запиту, який уже є саме для такого випадку —
  не помилка коректності, лише зайве навантаження на великих бібліотеках (1000+ книг).
- **`src/data/providers/index.ts` (`ALL_PROVIDERS`)** — порядок експорту не збігається з
  реальним пріоритетом пошуку; нешкідливо зараз, але пастка для майбутнього коду, що покладеться
  на цей порядок.
- **`catalogSync.ts`** — книга з кураторського джерела впливає на рахунок «Трендів» лише
  випадково (якщо в каталозі вже є рядок з тим самим ISBN від іншого провайдера) — задокументо-
  ваний намір ("Тренди" — органічний сигнал) залежить від збігу, не явного правила.
- **`app/journal/index.tsx` (`feedEntryLabel`)** — без захисного фолбеку на нерозпізнаний
  `entry.type`, на відміну від сусіднього `src/lib/journalEntryLabel.ts`. Недосяжно зараз (тип
  обмежений `CHECK` на рівні БД), але пастка, якщо перелік типів колись розширять лише в одному
  з двох місць.
- **`app/memory/[workId].tsx`** — захоплення картки в зображення не чекає завантаження
  мережевої обкладинки; малоймовірно на практиці, не підтверджено.
- **Невідстежений файл у корені репозиторію:** `curated-books-guide.html` — робочий файл
  власника продукту, ніколи не комічений (репозиторію версійного контролю зараз узагалі немає)
  і не входить у жоден архів. Варто перенести в `data/`/`docs/` для порядку.
- **Застарілий route map у `docs/ARCHITECTURE.md` розділ 4** — вже позначений застарілим із
  прямим посиланням на актуальний перелік (цей документ, розділ 4.4) — не тиха розбіжність, а
  зафіксована.

## 12. Сьогоднішня робота (2026-09-10) — очищення кураторської добірки книг

Ще не відображено в жодному документі репозиторію, крім щойно доданого запису `CHANGELOG.md`
("Milestone 11, доповнення20") — коротко для повноти цього звіту:

Власник продукту реально прогнав поповнений `data/curated-books.csv` (2094 рядки) через
`scripts/sync-curated-books.js`: **1846 додано, 163 оновлено, 85 пропущено з помилкою**. Усі
85 розібрані й виправлені:

1. **55 точних дублікатів рядків** (не 53 — 2 пари виявились одночасно задовгими й
   задубльованими). Причина — випадково задвоєний блок ~150 рядків. Кожна пара програмно
   звірена (title/authors/isbn13/description побайтово) перед видаленням — 100% збіг у всіх
   55 випадках.
2. **30 задовгих `id`** (>100 символів, ліміт валідації) — новий скрипт
   `scripts/shorten-long-ids.js`: обрізає до ~90 символів по межі слова + детермінований
   8-символьний sha1-суфікс від оригінального `id`; якщо оригінал задубльований (перетин із
   п.1) — обом рядкам свідомо присвоюється ОДИН і той самий новий `id` (щоб не заховати
   дублікат від власної перевірки sync-скрипта, а не через недогляд).
3. **1 дублікат ISBN13 між двома різними `id`** (друковане й e-book видання «Драбини»
   Є. Кузнєцової з однаковим ISBN) — за рішенням власника продукту e-book рядок видалено.
4. **1 конфлікт з наявним записом бази** («Двір шипів і троянд» С. Дж. Маас, додано повторно
   під іншою транслітерацією `id`) — за рішенням власника продукту `id` перейменовано, щоб
   наступний sync оновив наявний запис.

Результат: 2094 → 2038 рядків, 0 залишкових проблем усіх 4 категорій при повторній перевірці.
`data/README.md` доповнено розділом про новий скрипт.

## 13. Рекомендований порядок дій перед/на початку V2

1. **Закрити відкритий 🔴 ризик безпеки** (ISBNdb-ключ, розділ 8) — найдорожчий за наслідками,
   найдешевший за впровадженням (Supabase Edge Function, той самий патерн, що вже є для
   каталогу). Потребує доступу власника продукту до Supabase CLI/дашборду — не автоматизовано
   досі саме через це.
2. **Підняти реальний CI** (GitHub Actions: `npm install && tsc --noEmit && jest`) — уперше
   отримати автоматичну перевірку коректності; заразом нарешті реально прогнати всі 13
   наявних тестів і побачити точний список CVE з `npm audit`.
3. **Додати мінімальний repository-рівень тестів** — саме цей шар зараз повністю непокритий,
   хоча містить найскладнішу логіку (union `note`/`quote` з приєднаннями, `countsByReaction`,
   `catalog_upsert_book`).
4. **Дрібний прибиральний прохід** (розділ 10): мертвий код, `curated-books-guide.html` поза
   контролем версій (сам репозиторій зараз узагалі не під git — варто це теж розглянути як
   окремий пункт V2-підготовки).
5. **Захистити `book-covers` bucket** (🟡, розділ 8) — той самий Edge Function або Anonymous
   Auth.
6. **Рішення про Auth/акаунти** (розділ 11) як передумова для соціальних функцій і «Дуету
   читання» — найбільший продуктовий крок V2 сам по собі, вимагає окремого планування
   (модель даних вже готова, рішення "опційний шар" уже прийняте власником продукту).
